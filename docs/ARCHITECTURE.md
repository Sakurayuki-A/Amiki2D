# Amiki2D 架构总览

## 分层

```
┌─────────────────────────────────────────────────────────┐
│  应用层   UI 框架 / 游戏 / 设计工具 / 文档查看器            │
├─────────────────────────────────────────────────────────┤
│  amiki（门面）                                            │
│    Canvas  —— 立即模式 API（类 Skia/Canvas2D）             │
│    Scene   —— 保留模式场景（编码流，可增量、可缓存）          │
├─────────────────────────────────────────────────────────┤
│  编码层  场景 → 紧凑编码流（tag + data，GPU 友好）          │
├─────────────────────────────────────────────────────────┤
│  后端抽象                                                 │
│   ├─ amiki-gpu    wgpu 计算着色器引擎（主线）               │
│   └─ amiki-raster CPU 引擎（参考实现 → SIMD/JIT 兜底）      │
├─────────────────────────────────────────────────────────┤
│  amiki-math  零依赖几何核心（曲线、变换、压平）              │
├─────────────────────────────────────────────────────────┤
│  平台    wgpu: Vulkan / D3D12 / Metal / WebGPU / GL       │
└─────────────────────────────────────────────────────────┘
```

设计原则：

1. **核心零依赖**：`amiki-math`/`amiki-scene` 不依赖任何第三方库，保证可被任意宿主嵌入
   （对标 Skia 以 C++ 为核心、Skija 等只是绑定的结构）。
2. **场景与后端解耦**：上层只产出 Scene，后端消费 Scene。同一 Scene 可渲染到 GPU 纹理、
   窗口表面或 CPU 像素缓冲，结果算法级一致（CPU 参考实现就是 GPU 的对拍基准）。
3. **算法先行**：每个渲染特性先在 CPU 参考实现中确立精确算法，再移植 WGSL —— 两个实现
   共享同一份数学（解析式覆盖率积分），以 brute-force 超采样作为第三方裁判。

## 数据流（M3：稀疏桶表全 GPU 管线，当前默认）

```
PathBuilder ──► Scene (draws: transform + path + paint + clips + blend)
                    │
                    ▼
        CPU: 仿射变换 + 控制点/直线提取（不压平、不分箱）──► GPU 上传
                    │
                    ▼
  ┌─ enc1a：分箱结构（规模 ∝ draws × tile 行）────────────────────┐
  │  clear strips → flatten（均匀压平）→ strip 归并（活跃 tile bbox）│
  │  → measure → 3×前缀和 → tile 行活跃列表 → 逐 tile 桶表          │
  └──────────────────────────── 〖读回 32B 规模〗──────────────────┘
  ┌─ enc1b：稀疏单元（规模 ∝ 画面内容）───────────────────────────┐
  │  clear → emit（成员计数 + carry 定点桶）                        │
  └──────────────────────────── 〖读回 32B 成员数〗────────────────┘
  ┌─ enc2：CSR → 桶表 → 着色 ─────────────────────────────────────┐
  │  scan(单元 CSR) → tile_fill → scatter(段端点) → carry → fine    │
  └────────────────────────────────────────────────────────────────┘
                    │
                    ▼
        surface blit / 读回 PNG
```

每 workgroup = 一 tile、每线程 = 一像素；fine 逐像素只遍历覆盖本 tile 的 draw
（逐 tile 桶表，d 递增 = 画家序），显存与逐像素工作量都随画面实际内容伸缩。
稠密网格（M2f）保留为对拍基准：两条路径渲染逐字节一致（`sparse_matches_dense`）。

## 关键取舍

- **压平放 GPU（M2 起）**：均匀并行压平 + 闭式可证明段数界（误差界在 CPU 端推导）。
- **分箱放 GPU（M2f/M3）**：`counts` 前缀和 → 段池 → 稀疏桶表，全程 compute pass。
- **两代分箱并存**：稀疏为主线，稠密为参照；对拍断言保证二者等价，迁移无回归风险。
- **混合模式 src-over、sRGB 空间直接混合（M1）**：业界默认做法；M4 引入线性光照
  （rgba16float 渲染目标）与色彩管理，这是"引领"而非跟随的一部分。
- **每像素无状态面积积分**：不需要跨像素扫描状态，天然并行、天然适合 GPU；
  这正是选择该算法体系（而非传统 AET 扫描线）的核心理由。
