## ① 帧路径 `< 6 ms` 这条判据怎么处理

### 实测

```
prepare 1.06 ms + render_into 6.63 ms + poll 0.01 ms = 7.70 ms
```

`render_into` 返回时 GPU 已经干完（随后 `poll` 仅 0.01 ms）—— **86% 的时间在 GPU 上**。

> 所以这条判据**不可能靠优化 CPU 达成**。发布计划把「提取 <0.8 ms」与
> 「帧路径 <6 ms」并列，隐含假设"CPU 提取消掉就能到 6 ms"——**这个假设是错的**。
> 我已按实测更正了计划，但**判据本身要改成什么，需要你定**。

### 选项

| 选项 | 说明 |
|---|---|
| **A. 改成 GPU 侧指标** | 例如「GPU 时间 < 3 ms」或「主机侧 < 3 ms」。目标变得可测量、可达成 |
| **B. 推到 M7** | 承认它是 GPU 侧工作（更快的分箱/着色），本版不承诺 |
| **C. 改成"内容规模"指标** | 例如「10 万条曲线仍能 60 fps」——更贴近用户感知，但要先定义场景 |

### 建议

**A + B 组合**：本版把判据改成可验证的 GPU 侧指标（A），
同时把"帧路径总墙钟"明确列为 M7 目标（B）。

### 影响

纯文档改动，不影响代码。**但它是发布判据的一部分 —— 不改成可达成/可测量的形式，
判据就永远满足不了。**

## ② 启动开销的默认策略

### 实测（RTX 3050 / Windows / release / 冷启动）

| 配置 | 冷 | 热 | 达标（<200 ms） |
|---|---|---|---|
| **默认**（全部后端 → 本机选 Vulkan） | **337 ms** | 202 ms | ✗ |
| `AMIKI_BACKENDS=vulkan` | **154 ms** | 53 ms | ✓ |
| `AMIKI_BACKENDS=dx12` | 2272 ms | 2093 ms | ✗ |

启动开销的 **86% 在 `Instance` + 请求适配器**（后端枚举各自加载驱动），
全部 21 条管线只占 **12.7 ms** —— 所以计划里"用 PipelineCache / 惰性创建"的
假设是**错的**。

### 选项

| 选项 | 代价 |
|---|---|
| **A. 保持现状**（默认全后端） | 默认可移植，启动 337 ms 不达标 |
| **B. 平台默认后端**（Windows→DX12、macOS→Metal、Linux→Vulkan） | Windows 上 DX12 冷启动 **2.3 s**（FXC 运行期编译），**比现在还差** ✗ |
| **C. 先试快路径再回退**（如先 Vulkan，拿不到适配器再全后端） | 在这台机器上 154 ms ✓；但把"首选后端"写进引擎默认值，削弱"一套 WGSL 通吃"的承诺 |
| **D. 不改进引擎，由应用侧解决** | `new()` 本来就是 `async` —— 应用可与窗口初始化**重叠**，不让驱动初始化阻塞首帧 |

### 建议

**D 为主、A 为辅**：引擎保持"默认可移植"，把"启动延迟"作为**应用侧**的问题来解
（`async` 构造函数就是为此准备的）。若你希望引擎自己处理，选 C，但要接受
它把某个后端写进了默认值。

### 影响

选 C 需要改 `GpuRenderer::new()` 的默认值（约 10 行）。
选 D 只需在文档与示例里示范"如何重叠初始化"。

## ③ 要不要为了提取性能引入更强的并行手段

### 背景

提取的瓶颈已定位：**每帧约 10 万次内存写**（`Vec::push`），
不是计算、也不是遍历（"只走路径"仅占 6%）。已通过"批量写代替逐次 push"
把中位数做到 **798.5 µs**（判据 800，余量 0.2%，在噪声内）。

再上一个台阶需要**改数据布局**（例如把 draw 索引并进图元自身的空位），
那会牵动 WGSL 侧的读取方式。

而**并行**这条路已经被实测否定：

| 线程数 | 1 | 2 | 4 | 8 | 12 |
|---|---|---|---|---|---|
| 耗时 | **0.70–0.91 ms** | 1.02–1.68 | 1.18–1.53 | 1.22–1.69 | 1.27–1.62 |

已排除线程创建开销（304 µs）与分配器争用（预分配无改善）；
同机纯计算负载能加速 **4.43×**，说明机器能并行、是**这个负载**并行不了。

### 如果你想让并行真正可用，三条路

| 选项 | 代价 |
|---|---|
| **A. 引入 `rayon`** | 一行依赖；但它自己用 `unsafe` + 常驻线程池。**项目明确"保持依赖轻量"**，需你同意 |
| **B. 自建常驻线程池** | 基于 `std::sync::mpsc`，只建一次跨帧复用。**但任务借用 `&Scene`，安全 Rust 下做不到 `'static`** —— 要么 `Arc<Scene>` 深拷贝（太贵）、要么 `unsafe`（项目 `forbid(unsafe_code)`） |
| **C. 接受现状** | 提取已临界达标；把精力放到 GPU 侧（真正的瓶颈） |

### 建议

**C**。理由：提取已经达标（临界），而**帧路径的瓶颈在 GPU 不在 CPU** ——
即使提取变成 0，帧路径也只从 7.70 降到 7.64 ms。为它引入依赖或 `unsafe`，
投入产出不成立。

### 影响

选 A/B 涉及项目的依赖与安全策略，是**方向性**决定，不只是性能取舍。
