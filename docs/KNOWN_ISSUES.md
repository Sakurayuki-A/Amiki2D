## A. 未验证项（客观条件所限，不是"已通过"）

### A1 跨厂商硬件未验证（**已知限制，非待办**）

本版本仅在 **NVIDIA RTX 3050 / Windows** 上完成三后端验证。
**AMD、Intel、Apple Silicon、移动 GPU 未测试。**
**不承诺跨厂商像素一致。**

**为什么是"已知限制"而不是"待办"**：这是单人开源项目，没有第二块 GPU。
把它挂在路线图上只会让后续工作停摆 —— 而它在**技术上是可验证的**，
只是需要硬件。所以处理方式是：

- **登记**：就是上面这段，以及 README 里的一句话
- **留钩子**：[`tools/verify_gpu.sh`](../tools/verify_gpu.sh) —— 一条命令跑完
  三后端验证并打印可直接贴进 issue 的结果表。**作者不跑，别人可能会跑；
  没人跑也没有损失。**
- **不在路线图上**

**这条限制的实际含义**（说实话，不淡化）：

三个后端在**同一块 GPU** 上都跑通了，但"同一块 GPU"意味着
**驱动与硬件的组合只覆盖了一种**。执行这条验证时抓到过两个
"一换后端就起不来"的真 bug（DX12 的 FXC 循环展开失败、
GL 的 `textureSize` 类型不匹配），所以未验证意味着**可能还存在
厂商/驱动相关的未知问题** —— 特别是：

| 未覆盖 | 潜在风险 |
|---|---|
| AMD / Intel 的 Vulkan 驱动 | WGSL 编译差异、浮点行为差异 |
| Apple Silicon（Metal） | 该后端**从未跑过任何测试** |
| 移动 GPU | 精度与 limits 差异 |

**用户如果撞到问题**：请附上 `tools/verify_gpu.sh` 的输出提 issue ——
那正是这个钩子存在的意义。

## A. 未验证项

### A2 WASM 的 WebGPU 构建未验证（**已知限制，非待办**）

**当前 WASM 构建是纯 CPU 的**（关掉了 `gpu` feature），模块 **~966 KB**，
与原生 CPU 后端输出**字节一致** —— 0.6.0 起这半边有了**三浏览器实测**：
同一场景（含文本、渐变、位图、模糊层）在 **Chrome / Edge / Firefox**（均无头）
渲染并哈希对比，三者与原生 CPU 输出**逐字节一致**
（SHA-256 `d565cc36…`，验证页 `examples/wasm/browser_test.html`）。

**浏览器里能不能走 GPU：不仅未验证，还有已查明的架构阻塞**（0.6.0 探路结论）：

- 编译可行：`--features gpu` 的 wasm 模块 **2.5 MB**（远低于早先 23 MB 的预估），
  经 wasm-bindgen CLI 胶水后 **1.43 MB**，C ABI 导出完整保留，CPU 路径可用
- **阻塞点**：`amiki_context_create` 是同步的，而 WebGPU 初始化是异步的 ——
  引擎用 `pollster::block_on` 同步等待，实测在无 WebGPU 的环境直接
  panic-abort（wasm 构建为 `panic=abort`），在真实浏览器主线程则会**死锁**
  （被阻塞的事件循环永远等不到异步请求完成）。解法需要 **C ABI 层的异步
  重构**（GPU 上下文异步创建或就绪轮询），是设计变更而非稳定性修复

**为什么这是限制而不是待办**：纯 CPU 构建已覆盖 WASM 的主要用途且三浏览器
验证通过；GPU 那条路的代价是一次 ABI 设计变更。**留待有真实需求时再做。**

## B. 已知限制（有意的边界：显式报错或明确降级）

### B1 GL 后端不支持位图

GL 读不出 `texture_2d_array`（实测采样恒为不透明黑）。引擎**显式报错**
并提示改用 Vulkan/DX12 或 CPU 引擎 —— **不会静默画错**。
代码：`crates/amiki-gpu/src/lib.rs:229`。

### B2 字体格式有限

`amiki-text` 支持 TrueType / OpenType，**不支持 `.ttc` 字体集合与 `.woff` / `.woff2`**。
代码：`crates/amiki-text/src/lib.rs:63`。

### B3 AMK1 编码流不内嵌位图

编码流无法表达"内嵌位图"的绘制，解码时**显式报错**。
代码：`crates/amiki-scene/src/lib.rs:1220`。

### B4 位图缩小没有多级过滤（无 mipmap）—— **已修复（0.6.0）**

> **这一条已关闭。**
>
> - **mip 链在 CPU 生成**（`amiki_scene::mipmap`）：2×2 盒式滤波，
>   **线性光空间 + 预乘 alpha** 上平均（线性平均有专项测试钉住：
>   黑白棋盘的平均是 sRGB 188 而不是 128；透明边缘不发黑）。
>   不用 GPU 生成 —— 两套滤波实现必然漂移。
> - **LOD 在 CPU 算好**（`compute_lod`，从放置轴向量的逆雅可比出发），
>   打包进 GPU 放置缓冲的空闲分量，WGSL 只读不算 —— `log2` 在 CPU libm
>   与 GPU 内建函数间可能差 1 ULP，采样层级对它敏感，宿主算好打包
>   就消掉了这个漂移源。
> - GPU 数组纹理开 mip 层逐级上传；`mipmap_filter: Linear` +
>   `textureSampleLevel` 显式 LOD 做三线性。
> - **顺带修掉一个潜伏 bug**（对拍首次暴露）：平铺采样在接缝半纹素处
>   GPU 钳边、CPU 回绕 —— 原来只有 ClampToEdge 一个采样器，
>   uv 落在 [0,1] 边缘 ~1.6% 带内时跨层取纹素被钳住。
>   修复：新增 Repeat 地址模式采样器（binding 17），真回绕发生在采样器上。
> - C ABI：`amiki_image_create_rgba8` **默认生成链**（+1/3 内存），
>   `amiki_image_set_mipmap_mode` 可关；`amiki_canvas_set_mip_bias` 可调层级
>   （非有限值与越界枚举显式拒绝且不改状态）。
> - AMK1 编码流**不变**：mip 链是运行时派生物，场景文件仍只存原图。
>
> **验证**：`gpu_image_mipmap_matches_cpu`（缩小 / 缩小+旋转 / 缩小+平铺，
> 最大通道差 **1**）；奈奎斯特后缩小整幅均匀灰 ≈188（摩尔纹消除的量化判定）；
> 1:1 与放大时带链与不带链**逐字节一致**；`verify.cmd` 符号数 72 → **74**。
>
> 仍不做：各向异性过滤；GPU 生成 mip 链；纹理压缩。

**以下为修复前的记录，保留以便对照：**

所有纹理 `mip_level_count: 1`、`mipmap_filter: Nearest`。
**位图大幅缩小时会走样**（只有线性采样，没有 mip 链）。
影响：UI 里把大图缩成小图标这类用法。**这是当前最容易在真实使用中撞到的限制。**

### B5 even-odd 填充规则未实现 —— **已关闭（0.8.0）**

**原状**：`FillRule` 枚举只有 `NonZero`，源码里 `even_odd` 出现 0 次。
影响：需要"奇偶填充"的图形（同向嵌套环、自相交多边形、部分字体轮廓的镂空）
只能靠调用方自己反向绕行来绕开。

**0.8.0 关闭方式（与最初计划不同，原因是实测反证）**：计划的"复用 `seg_area`、
只改累加符号、取 Σ 的奇偶性"**不可行** —— 引擎的覆盖率是绕数加权面积
`∬ W dA`，而 even-odd 要的是它的非线性函数（`W mod 2`）。实测偏差：
普通方块 **0.7207**（≈184/255）、同向双环 **0.8477**（≈216/255），
解析抗锯齿会整个丢掉（证据：`crates/amiki-raster/tests/fill_rule_semantics.rs`）。

改用的做法是**几何预处理**：把 even-odd 的路径按 y 扫描成带、带内按 x 排序、
两两配对成**互不重叠的梯形**（每个只输出两条竖边），再走原有的 NonZero 路径 ——
覆盖率数学与 WGSL 一行未改。与 32× 超采样 even-odd 裁判的偏差：
简单方块 0.0175、三层嵌套 0.0209、自相交五角星 **0.0027**。

**代价（写在明处，不是缺陷但要知道）**：
- even-odd 的 draw 每帧多做一趟 CPU 侧压平 + 跨度分解（**不缓存**），
  上传的线段数也明显多于原曲线数 ⇒ even-odd 比 NonZero 贵。
- 想做"按路径哈希缓存分解结果"的话，那是一条独立的技术债（未登记编号）。

**不做的部分**：其他填充规则（Positive / Negative / Winding）、描边的 fill_rule
（描边是轮廓化，与填充规则无关）。

### B6 CPU 参考光栅器：含层场景仍回落全量渲染

`amiki-raster` 遇到含离屏层的场景时**整幅重画**（注释说明：滤波需要整层完整内容，
只重算部分 tile 会让模糊读到残缺数据 → 选择"慢但正确"）。
**GPU 路径已在 P0-2 解决**（层缓冲跨帧复用，省 96.5% tile），但 **CPU 路径没有**。
影响：CPU 参考实现的性能，不影响正确性。
代码：`crates/amiki-raster/src/lib.rs:1068`。

### B7 DX12 冷启动约 2.3 s

FXC 在**运行期**编译着色器（`static-dxc` 预编译方案试过，其依赖会在构建期下载
DXC 而挂住，已放弃）。**不是引擎代码慢**；Vulkan 后端冷启动 61 ms。

### B8 `TIMESTAMP_QUERY` 不可用时无 GPU 计时

优雅降级：`timestamps.supported = false`，但**主机侧计时仍然有效** ✓
所以 `FrameProfile` 同时给两者。

### B9 超长单词无法放入 `max_width`

排版层会报告这一情况（不是崩溃、也不是静默截断），调用方自行决定如何处理。

### B10 提取的性能余量不大

0.586–0.617 ms vs 判据 0.8 ms（约 **26% 余量**）。
机制是明确的（消除每帧分配），但若未来场景复杂度上升，余量会被吃掉。

### B11 帧路径的最大单项是"保护性同步读回"

4.3–4.6 ms，占帧路径一半以上。**这是有意的正确性开销**
（投机分配必须读回实际用量才能确认没溢出，否则可能呈现残缺帧），
对应发布判据第 3 条。**它同时是帧路径性能的天花板** ——
要再快需要把流水线改成 GPU 驱动（异步校验），属 M7 级别工作。

### B14 并发创建 context 在**启用 Vulkan 校验层**时会崩掉进程（0.6.1 查明）

> **这不是测试环境的问题，而是 ABI 的调用约束** —— 真实应用若在 debug/校验构建下
> 在线程池里预热多个 context，一样会崩。（原先记在 D5，按"测试跑法"处理；
> 隔离实验证明与测试无关，故升级到这里。**但影响范围仅限校验层开启时**，
> 见下面的 A/B。）

`amiki_context_create` 在 `AMIKI_BACKEND_GPU` / `AMIKI_BACKEND_AUTO` 下会创建
`wgpu::Device`（`AMIKI_BACKEND_CPU` **不创建**）。多个线程**同时**创建时，
若 **Vulkan 校验层处于启用状态**，整个进程异常退出：

```text
0xC0000005（访问违例）—— 不是 panic，没有任何可捕获的错误
```

**根因（实测 A/B，同一份代码、同一台机器、同一个负载）**：wgpu 在
`debug_assertions` 下默认把 `InstanceFlags::VALIDATION` 打开，Vulkan 后端据此加载
**`VkLayer_khronos_validation.dll`**；该校验层在并发创建 Instance/Device 时会崩。
**不是引擎、也不是显卡驱动的问题。**

| 条件 | 崩溃 |
|---|---|
| 校验层**开**（debug 默认），16 线程并发创建 | **3 / 6** |
| 校验层**关**（`InstanceFlags::empty()`），同一负载 | **0 / 6** |
| 校验层开，4 线程并发创建 | 0 / 6 |
| 校验层开，串行创建 16 个 → 16 线程**并发使用** | **0 / 5** |

**独立佐证**（Windows 事件日志，三次崩溃一一对应）：

```text
Faulting application name: amiki_gpu-*.exe
Faulting module name: VkLayer_khronos_validation.dll      ← 校验层
Exception code: 0xc0000005
```

**影响范围（关键）**：

- **release 构建默认不启用校验层 ⇒ 不受这条约束影响。** 发布给用户的应用没有这个问题。
- 受影响的只有 **debug 构建**，或**显式打开 wgpu 校验**的运行（含 `cargo test` 的默认配置）。
- 这也解释了 §8.5 那条"不可复现"：`docs/VERIFY.md` 的清单一直用
  `cargo test --release`（**校验层关**），而那次失败发生在默认（debug）配置下
  —— **两次不是同一套条件**，所以怎么重跑都对不上。

**约束**（已写进 `crates/amiki-capi/include/amiki.h` 的「线程模型」与
`crates/amiki-capi/README.md`、`docs/API.md`）：

- ✅ **并行使用**不同 context：安全 —— ABI 原来那句"不同 context 之间可以并行"
  说的是使用，这一半**成立**；
- ❌ **并行创建**：必须先在单线程里依次建好所需数量，再分发给各线程。
  release 构建未观察到问题，但**不要依赖构建类型** —— 统一按串行创建写。

**为什么必须写在明处**：这是本项目"不支持就**显式报错**"原则的**反例** ——
并发创建既不返回错误码、也不 panic，而是直接崩进程，调用方拿不到任何线索。

**阈值不精确**：4 线程 0/6、16 线程 3/6，中间没有细测；阈值与驱动/机器相关，
**不要把它读成"多少线程以下就安全"的承诺**。

**后续处置（仍**建议**做，本次只登记 + 写文档；注意它的价值已经变小）**：

1. **引擎内部串行化创建**（推荐）：`GpuRenderer::new()` 里给"Instance/适配器/设备
   创建"加一把进程级锁。release 下无竞争、代价可忽略；debug 下消除崩溃。
   代价是"引擎不做内部同步"这条设计声明要加一个例外（只影响创建，不影响渲染）。
2. **ABI 层显式拒绝**：用 `AtomicBool` 检测"正在创建"，第二个进来的线程返回错误码。
   符合"不静默出错"，但会把**偶发崩溃**变成**必然失败**，需要调用方处理错误。
3. **什么都不做**（现状）：只保留测试侧的串行闸门。可接受，因为发布构建不受影响。

**测试侧**：`amiki-gpu` 的 GPU 测试因此共用一个串行闸门（`tests.rs` 的
`GPU_TEST_LOCK` / `gpu()`）—— 默认线程下 **6 / 6 全绿**（此前 **4 / 6** 崩）；
`--test-threads=1/2/4` 也都不崩。顺带消掉了"性能断言在并行环境里失真"这个
反复出现的假失败来源（见 `HANDOFF.md` 纪律第 7 条）。
**若再遇到"测试失败但没有任何输出"**：先按"是 panic 还是进程被杀"分流
（前者有栈，后者没有，实测退出码 `0xC0000005`），再用 `--test-threads` 做梯度
实验确认是不是并发度问题 —— 不要先怀疑渲染数学。

### B15 无字体回退（一段文本只能用一种字体）—— **已关闭（0.7.0）**

**原状**：`amiki_text::shape(font, …)` 与 `amiki_layout::layout(font, …)` 只接受
**一个** `Font`，于是"支持 CJK"实际上要求调用方**自己为每段文本挑对字体**：
只加载 Inter 时整段中文画成方框（`window_demo` 之前就是这样）。

**为什么这条值得单独记**：断行/禁则的测试一直是拿**显式传入的 Noto** 跑的，
所以"测试全绿"与"默认可用的路径是坏的"**同时成立** —— 这正是"声称能力"与
"可用能力"之间的缺口。它此前只写在 `docs/API.md` 的限制表里，没有编号，
也就没有"关闭它"的动作。

**0.7.0 怎么关的**：新增 `FontStack`（有序字体栈）+ `shape_with_stack` /
`layout_with_stack` / `Canvas::text_with_stack`；缺字策略显式可选
（默认 `Error` 报错，可切 `.notdef` 或跳过）。**老入口一字未动**，
并有用例断言"单字体栈与老路径**逐字节一致**"（`f32::to_bits` 相等）。

> ⚠️ **B2 仍然成立，别混为一谈**：[B2](#b2-字体格式有限) 说的是**字体格式**
> （不支持 `.ttc` / `.woff` / `.woff2`），与"字体回退"是两件事 ——
> 本版没有让 `.woff` 变得可用。

### B16 `|W| ≥ 2` 区域的边缘覆盖率会饱和（**既有**精度限制，0.8.0 查明）

**现象**：覆盖率是 `min(|Σ seg_area|, 1)`，几何上等于 `∬ W dA`。
在**绕数 ≥ 2 的区域边缘**，这个量会**饱和**：一个像素被 |W| = 2 的区域覆盖
比例 `f ≥ 0.5` 时，`2f` 被钳到 1，而真实覆盖率只有 `f`。

**实测**（参照是独立的 32× 超采样逐点绕数裁判）：
自相交五角星（`{5/2}`）上 NonZero 的最大偏差 **0.1387**（≈35/255，出现在
中心五星与臂的交界处）。

**为什么登记**：这是"看起来只是边缘略胖"的**静默**精度损失，不报错、不崩，
也没有任何测试在用严格容差盯着它（既有用例的容差是 0.03，而这个形状的偏差是 0.1387 ✗
—— 也就是说既有用例**没覆盖到**这类形状）。

**影响范围与不影响的**：
- 只影响**自相交**或**同向重叠**（|W| ≥ 2）的路径边缘；简单形状完全不受影响。
- **even-odd 不受影响**：0.8.0 的 even-odd 走"互不重叠的梯形"，其和恒 ≤ 1、
  不会触发饱和（同一张五角星上 even-odd 与裁判的偏差只有 **0.0027**）。
- 与 `B5` 的关闭无关：本版**没有改** nonzero 的覆盖率数学（一行未改）。

**后续处置（未决策）**：真正修它需要"按区域分解 + 分别求覆盖"（等于把
even-odd 那套预处理推广到 nonzero），代价与风险都不小；在那之前，
**调用方若要严格精度，应避免使用自相交路径**（或改用 even-odd + 等价几何）。

## C. 明确不做（已决定的边界，避免范围蔓延）

| # | 项 | 理由 |
|---|---|---|
| C1 | **双向文本**（阿拉伯/希伯来） | 面向特定语言；需要独立的 bidi 算法 + 字形重排序 |
| C2 | **Knuth-Plass 全局最优断行** | 排版**质量**提升，不是能力缺失；贪心断行已可用 |
| C3 | **宽色域**（Display P3 / Rec.2020） | 色彩能力的另一半。与"通用 2D"正交，需要整套色彩管理 |
| ~~C4~~ | ~~C ABI / WASM~~ | **已做** —— 见下方「已移出本表」 |
| C5 | **CPU 引擎 SIMD / 多线程** | 并行实测**无效**（从 2 线程起单调变差）；真实瓶颈是分配而非计算，且目标已达成 |

### 已移出本表（原"明确不做"，现在做了）

**C4 C ABI / WASM** —— **两者都已完成**：

- **C ABI** 于 **0.4.0** 落地：手写 `amiki.h` 契约、**72 个导出符号**、
  C / C# / Node 三个绑定示例输出**字节一致**（`crates/amiki-capi/`）
- **WASM** 于 **0.5.0** 落地：模块 **950.7 KB**（纯 CPU 构建），
  与原生 CPU 后端输出**字节一致**（`crates/amiki-capi/examples/wasm/`）

**C3 的一半也做了**：**HDR** 于 0.5.0 落地（>1.0 穿过层边界存活 +
可选色调映射，见 `docs/COLOR.md`）。**宽色域仍未做**，所以 C3 这一行保留，
但已收窄为"宽色域"。

> 顺带记一条经验：`examples/node/` 用的是 **koffi FFI 而不是 WASM** ——
> 它证明的是"C ABI 可被非 C / 非 .NET 运行时调用"。
> **别把这两件事混为一谈**，它们是两个不同的交付。

## D. 技术债

### D1 `docs/` 与代码注释的历史漂移

本次审计清掉了 5 处（README 两处状态段、OVERVIEW 14 处、`FillRule` 的
"even-odd 在路线图 M2"、`extract.rs` 的"常驻线程池属后续工作"）。
**这类问题会反复出现** —— 每次里程碑推进后都应扫一遍"承诺未来"的措辞。

**建议**：把"扫过时断言"作为每次收工的固定步骤（本次已加入 `docs/HANDOFF.md` 的纪律）。

### D2 两份文档示例标了 `ignore`

`Canvas::push_layer_filtered` 与 `Canvas::text` 的 doc 代码块是 `ignore`，
即**不在 `cargo test` 中执行**。它们可能已经与实际 API 不符。

### D3 `clip_texs` 字段需要 `#[allow(dead_code)]`

该字段只用于持有纹理生命周期（`clip_views` 借用它们），从不被读。
已加说明注释，属**有意为之**，不是疏漏。

### D4 基准用例只有一条"复用"口径

`cpu_extract` 的 `1080p_10k_curves_reused` 是判据口径，但其余两个用例
（`720p_64` / `1080p_1000`）仍是"一次性调用"口径。**两者不可比**，
未来加用例时要保持口径标注一致。

### D5 even-odd 的跨度分解结果**没有缓存**（0.9.0 登记）

`amiki_raster::even_odd_spans`（0.8.0 引入）在**每次绘制**时都要：
CPU 侧压平路径 → 按 y 扫描成带 → 带内按 x 排序、按交点切分 → 两两配对。
对同一个 even-odd 路径逐帧重画（动画、滚动列表里的星形图标等）就是逐帧重算。

**影响**：只有 even-odd 的 draw 付这个成本（nonzero 与 0.8.0 之前完全一样）；
正确性不受影响，是**性能**问题。

**为什么没顺手做缓存**：缓存键要选得对（路径哈希？几何哈希？变换要不要进键？），
而变换在 `flatten_draw` 里就被吃掉了 —— 用"设备空间线段表"做键最稳（但那就是
每次都要先压平，省不掉最贵的一步）。这是个**需要先想清楚键与失效条件**的设计，
不适合塞在 0.9.0 里顺手做。

**处置（未决策）**：可选方案——(a) 调用方自己缓存 `Path`（门面层）；
(b) 引擎内按"路径元素 + 变换"做 LRU（引入缓存失效与内存上限问题）；
(c) 把分解下沉到 GPU（但配对需要排序，并行内核做不了，见 `even_odd.rs` 的说明）。

## 附：判定"是否算问题"的取舍原则

本项目一贯的取舍（写在这里，避免每次重新讨论）：

> **不支持就显式报错，不静默画错。**

所以 B1/B3/B9 这些"做不到就报错"的项，虽然列在限制里，
但**它们的行为是正确的** —— 真正的问题只有两类：
**静默画错**（当前没有已知的）与**能力缺失但用户以为有**（靠这份清单避免）。
