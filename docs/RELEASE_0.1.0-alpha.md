# Amiki2D 0.1.0-alpha 发布报告

**发布日期**：2026-09-30
**版本**：`0.1.0-alpha`（`workspace.package.version`，五个 crate 统一继承）
**范围**：M1–M3 完成 + M3.5 完成 + M3.6 起步

---

## 一、这是什么

下一代通用 2D 渲染引擎的首个 Alpha。技术主线是 **GPU 计算着色器 + 解析式覆盖率**：
路径压平 → 分箱 → tile 级解析式覆盖率积分。抗锯齿不是"近似采样"，而是
**逐像素的数学面积积分**。

相对传统光栅器的核心差异：**显存与画面实际内容成比例**，而非与画布面积成比例。
1080p × 10k 曲线实测 **20.93 GB → 34.5 MB（约 600×）**。

Alpha 的语义：核心管线可用且经双端对拍验证，但**内容能力不完整**、**API 未承诺稳定**。

## 三、能力清单

### 已实现

- 仿射变换（先变换后压平，ε 恒以设备像素度量）
- 二次/三次贝塞尔、任意多边形；nonzero 填充
- **解析式 AA**：与 64× 超采样 brute-force 对拍误差 < 0.03/像素
- **双压平器**：CPU 误差界自适应二分 + GPU 均匀压平（闭式可证明段数界）
- **稀疏桶表全 GPU 分箱（默认）**；稠密网格保留为对拍基准
- **16 种 W3C 混合模式**（含 HSL 非可分离四模式）
- **裁剪合成**：覆盖率纹理逐像素乘入，≤4 层嵌套
- **AMK1 编码流**：紧凑二进制场景格式
- **可诊断性**（M3.5）：稀疏自洽检查、`dump_sparse`、容量预检、`FrameProfile`
  分段计时、逐 pass GPU 归因（稀疏 10 段）
- **门面 API**：`Canvas` 立即模式 + headless PNG + winit 动画示例

### 未实现（后续里程碑）

|---|---|

| 文本、渐变、图像、滤镜 | M4/M5/M6 |

| CPU 引擎 SIMD / 多线程 / JIT | M7 |
| C ABI / WASM / HDR | M8 |

## 四、性能（RTX 3050 / Vulkan）

### 渲染吞吐

| 场景 | 稠密网格（M2f） | 稀疏桶表（默认） |
|---|---|---|
| 720p × 64 曲线 | 2.630 ms | **0.090 ms**（约 29×） |
| 1080p × 10k 曲线 | 不可行（需 20.93 GB） | **2.55–2.97 ms** |
| 1080p × 10k 显存 | 20.93 GB | **34.5 MB**（约 600×） |

### 帧路径墙钟

| 场景 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 720p × 64 曲线 | 6.59 ms | **1.03 ms** | **−85%** |
| 1080p × 10k 曲线 | 12.68 ms | 12.68 ms | 未改善 |

**720p 的 85% 提升**来自 M3.6 的 **MAP_READ 暂存缓冲池**（读回不再每次新建缓冲 + 冷映射）。
机制已确认：读数 `读回2` 从 1.37 ms → 0.08 ms。

### 1080p×10k 的剩余缺口（M3.6，已重新测量与修正）

**原始诊断已被实测否定。** 原文档写的是"每帧重建约 30 个缓冲 + 3 次 submit
同步点导致约 9 ms 缺口"。补全测量盲区（`FrameProfile` 原先只测了第 3 次编码，
漏掉前两次编码与提交）并修正一处重复计数后，实测分解为：

```
主机侧（1080p×10k 曲线，基准路径）
  提取         2.03 ms   ← CPU 场景提取
  分配         0.13 ms   ← 池化 26 处缓冲的全部收益上限
  上传         0.97 ms
  编码1a+提交  0.33 ms
  编码1b+提交  0.09 ms
  编码2        0.06 ms
  提交2        0.08 ms
  读回1        2.35 ms   ← 最大单项
  读回2        0.20 ms
  ─────────────────────
  GPU 合计     2.83 ms
```

**两条原依据都不成立**：

1. 「每帧重建约 30 个缓冲」→ **分配仅 0.13 ms**。wgpu 缓冲创建是惰性的，
   实际显存由驱动内部池化。
2. 「3 次 submit 同步点」→ 三次编码**与提交合计仅 0.56 ms**。合并提交最多省 0.5 ms。

**真正的大项是读回1 = 2.35 ms**，而它其中 `enc1a` 的 GPU pass 合计只有
0.94 ms —— 约 1.4 ms 是**纯同步延迟**（fence 等待 + map 延迟），属延迟而非吞吐。
消除它的正确做法是**投机分配**：用上一帧测得的容量作为本帧起点，只在容量
不足时才重做该帧（需要溢出回退路径）。这与已有的帧间持久化方向一致。

### M3.6 的目标依赖 M7

即使**完全消除读回1**（省 2.35 ms），墙钟也只从约 10.4 ms 降到约 8 ms，
**仍远高于 GPU 的 2.83 ms** —— 因为剩下的**提取 2.03 ms 是纯 CPU 工作**
（场景 → 控制点/段数提取），属 **M7（CPU SIMD / 多线程）** 范畴。

因此 **「帧路径墙钟压向 GPU 时长」在 M3.6 自身范围内不可达**。
M3.6 能做到的是：消除读回同步（投机分配，约 2.4 ms）+ 池化（0.13 ms）
+ 合并提交（约 0.5 ms），合计把墙钟推向约 8 ms 量级；剩下的差距需要 M7。

> 版本注记：以上数字测于 0.2.0-alpha（`gpu_frame_path` 基准，RTX 3050）。
> 0.1.0-alpha 时的原始数字（11.96 / 2.97 / ~9 ms）已被本次重测取代。

### 启动开销

`GpuRenderer::new()` 首次约 **0.5–0.7 s**（21 条管线编译，无 `PipelineCache`）。
离屏一次性出图场景受此支配——示例打印的"渲染 xxx ms"包含这段启动，不是渲染耗时。

## 六、本版的关键判断（有意为之的设计取舍）

1. **稀疏为主、稠密为参照**：两条管线并存，用逐字节对拍保证等价，迁移无回归风险。
2. **自洽检查不依赖稠密**：因为稠密在 1080p 约 **129 draw** 就撞 128 MiB 绑定上限，
   大场景必须有独立的裁判。
3. **快照锚定 CPU 参考引擎**：它是零依赖纯 Rust 路径，不受 GPU 驱动/wgpu 版本影响，
   最适合当字节级锚点。
4. **snapshot 与对拍并存**：对拍是差分的（两边同时错就看不见），快照是绝对的。
5. **`RenderPath::Dense` 只服务小场景**：容量预检在超限时返回可读错误而非 panic，
   并明确建议降级到稀疏路径。

## 七、已知问题

1. **1080p×10k 帧路径约 10.4 ms**（GPU 2.83 ms）——剩余项以「读回1 同步 2.35 ms」
   与「CPU 提取 2.03 ms」为主；后者属 M7（见上文「M3.6 的目标依赖 M7」）
2. **启动 0.5–0.7 s** ——缺 `PipelineCache`
3. **无版本控制历史** ——本项目在发布时尚未初始化 git，仅有工作区外的文件级备份
4. **注释与文档为中文** ——代码标识符为英文
5. **`sparse_consistency_at_scale` 用 1080p×600** 而非 10k：转储要读回全部结构，
   10k 下 `cell_meta` 单项约 43 MB，太慢。10k 规模由 `sparse_scales_beyond_dense`
   从渲染与显存角度覆盖
6. **`benches/render.rs` 的"稠密上限 draw 31/71"是保守值**：按单维 65535 工作组估算，
   而实际 `clear` 用线性 2D 派发；真实瓶颈是绑定墙（720p 约 292 draw / 1080p 约 129 draw）。
   两套口径不同，见 `dense_capacity` 文档注释。
