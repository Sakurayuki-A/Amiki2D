## 下一个任务：M3.6 投机分配

### 已确认的实测分解（1080p×10k 曲线，`gpu_frame_path` 基准）

```
提取         2.03 ms   ← 纯 CPU，属 M7
分配         0.13 ms   ← 池化 26 处缓冲的全部收益上限
上传         0.97 ms
编码1a+提交  0.33 ms
编码1b+提交  0.09 ms
编码2        0.06 ms
提交2        0.08 ms
读回1        2.35 ms   ← 最大单项，其中约 1.4 ms 是纯 fence/map 延迟
读回2        0.20 ms
GPU 合计     2.83 ms
墙钟约 10.4 ms
```

### 两条原始依据已被实测否定（不要再做）

1. ❌「池化每帧重建的 ~26 个缓冲」→ 分配仅 **0.13 ms**。
   （wgpu 缓冲创建惰性，显存由驱动内部池化）
2. ❌「合并 3 次 submit」→ 三次编码+提交**合计仅 0.56 ms**。

### 正确的目标

**投机分配，消除读回1 的同步停顿（约 2.35 ms）。**

原理：稀疏结构规模只有 GPU 测量后才知道，所以原实现是
"提交 → 读回规模 → 分配 → 再提交"。改成把**上一帧实测的容量**作为本帧起点，
直接分配、不停顿；帧尾读一次实际用量更新容量。容量不足则**该帧作废、用实测值重做**。

### 进度：投机分配**已完成**

| 步 | 内容 | 状态 |
|---|---|---|
| 1 | `SparseCapacity` 结构 + 字段 + 学习侧 | ✅ `b6db3a0` |
| 2a | 重做机制：`_once` 返回溢出标志 + 外壳重做一次 | ✅ `03931c7` |
| 2b-A | 容量**按场景特征分表**（`SceneKey` + LRU + 放弃投机） | ✅ `1bd37af` |
| 2b/2c | 两处读回改容量查表 + 帧尾用量读回 | ✅ `c9660f8` |

### 实测结果

```
720p×64:   756 µs → 486 µs   (−36%)
1080p×10k: 10.41 ms → 10.00 ms (−4%)
```

小场景收益显著；大场景只有小幅正向 —— 因为 1080p 的主机侧成本主要落在
`提取`（CPU，属 M7）与 `上传`，而不是那两次读回停顿。

### 关键设计（改这块之前先读）

1. **容量必须按场景分表**，不能是单一全局值。两种全局做法都实测失败过：
   - **直接覆盖**：换场景即溢出 → 每帧作废重做
   - **只增不减**：变成过度分配 → 小场景被大场景的容量拖着，
     实测 720p×64 从 0.67 ms **退化到 2.09 ms**
2. `SceneKey = (宽, 高, draw 数, seg_bucket)`，其中 `seg_bucket` 是
   `total_segments` 向上到 2 的幂 —— 几何随动画变化时 key 才稳定。
   **不要在 key 里用未量化的 `total_segments`**（每帧都会 miss）。
3. 表有上限（8 项，LRU 淘汰）；某 key 连续溢出 2 次后**放弃它的投机**，
   退回每帧测量 —— 最坏情况只是回到没有投机时的性能，不会每帧作废重做。
4. 溢出重做**不清空容量**：`_once` 报溢出前已把实测用量记进该键的表项
   （那正是本帧需要的格数），故第二次必然容得下。

### 正确性依据（关键，不可省）

- 容量不足时超出的写入会被丢弃（naga 对 storage buffer 有边界检查）
- 因此**必须**在帧尾读一次实际用量来判断是否溢出 —— 它替代了 readback1 的停顿
- 溢出 ⇒ `_once` 返回 `true` ⇒ 外壳作废本帧并重做一次
- **绝不把残缺的画面交出去**

### 写这类测试的两个坑（都踩过）

1. **测试要有牙**：第一版检查的是溢出之后**下一帧**的像素，那时容量已被修正，
   即使完全取消失败重做测试也照样通过。**必须检查溢出帧本身**的像素。
   写完后用"临时取消重做"验证一次：应当 FAILED。
2. **`Copy-Item -Force` 会保留源文件的旧修改时间**，于是 `cargo test` 会
   **复用旧二进制**。我因此误判为"测试非确定性"，实际是构建陈旧。
   还原文件后必须显式刷新时间戳，或改用正常编辑写入。
