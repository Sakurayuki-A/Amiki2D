## ① 帧路径判据：保留保护机制，判据拆成三项

### 遇到的问题

原判据是「帧路径总墙钟 < 6 ms」。实测后确认它把**三种性质完全不同**的东西
混在一个数字里：

| 部分 | 量 | 性质 |
|---|---|---|
| 主机侧渲染（提取 + 分配 + 上传 + 编码） | 2.2–2.8 ms | **可优化的对象** |
| GPU pass（时间戳实测） | 2.1 ms | GPU 计算 |
| **保护性同步读回** | 4.3–4.6 ms | **正确性开销** |

混在一起时，这个数字**既指导不了优化**（不知道动哪边），
也会**诱导去砍第三项**。

### 第三项是什么、为什么不能砍

`sparse.rs` 的投机分配路径（容量已缓存 = 稳态）：

```rust
let (usage, overflow) = if speculative {
    let bytes = self.read_buffer(&stats_buf, 32)?;   // ← 每帧一次 GPU 同步
    ...判断是否溢出，溢出则本帧作废重做
}
```

投机分配只知道"分配了多少"，**必须读回"实际用了多少"**才能确认没溢出；
溢出的那一帧画面是残缺的。这是一次
**"用一次同步换'绝不静默画出残缺帧'"** 的取舍，
直接对应发布判据第 3 条。

### 决定与实施

保留该机制，把判据拆成三项，并**写进代码**而不只是文档：

- `FrameProfile::host_render_ms()` —— 提取 + 分配 + 上传 + 编码（判据 < 3 ms）
- `FrameProfile::safety_readback_ms()` —— 保护性同步读回（只设上限）
- GPU pass 用 `timestamps` 合计（判据 < 5 ms）
- 总墙钟**只记录**，不设"必须 < 6 ms"（那要求砍掉第三项）

并由 `profile_frame_path_phases` 断言锁定。

> **曾考虑但否决的选项**：信任 N 帧后停止检测（降低保护强度 →
> 极端情况会漏掉溢出 = 静默残缺帧，正是判据 3 要防的）、
> 异步校验（`map_async` 下一帧检查，不牺牲正确性但发现时上一帧已呈现，
> 需应用侧双缓冲 —— 属 M7）。

> **口径更正**：本文档一度写过"帧路径 **86% 是 GPU 受限**，该判据不可能靠
> CPU 达成"。**那是错的** —— 它来自"`poll` 只花 0.01 ms"的**推断**，
> 不是测 GPU。补上时间戳后 GPU 只占 **27–43%**。

## ② 启动开销：平台首选 + 全量回退

### 实测（RTX 3050 / Windows / release / 冷启动）

| 配置 | 冷 |
|---|---|
| 默认（枚举全部后端） | **337 ms** ✗ |
| 仅 Vulkan | **154 ms** ✓ |
| 仅 DX12 | 2272 ms ✗ |

启动开销的 **86% 在后端枚举**（`Instance` + 请求适配器），
全部 21 条管线只占 **12.7 ms** —— 所以计划里"用 PipelineCache / 惰性创建"
的假设是**错的**。

### 决定与实施

**先试平台首选，拿不到适配器再回退到全部后端**：

- Windows / Linux → 首选 Vulkan（Windows 上 DX12 探测反而更贵）
- macOS → Metal
- 首选失败 → 回退 `Backends::all()`，并打印一行说明
- `AMIKI_BACKENDS` 仍可显式覆盖

**与之前那次"默认只用 Vulkan"的区别**：那次**没有回退**，等于把后端写死；
这次是"先走快路、走不通就全量兜底"，**可移植性没有变**。
引擎本身仍与图形 API 无关（同一份 WGSL 在三个后端上都跑通）。

**结果：337 → 61 ms** ✓ 判据 < 200 ms。

## ③ 是否为提取引入并行 / 依赖：不引入

### 曾考虑的三条路

| 选项 | 代价 |
|---|---|
| 引入 `rayon` | 一行依赖；但它自己用 `unsafe` + 常驻线程池，与"保持依赖轻量"冲突 |
| 自建常驻线程池 | 任务借用 `&Scene`，安全 Rust 下做不到 `'static` —— 要么 `Arc<Scene>` 深拷贝（太贵），要么 `unsafe`（项目 `forbid(unsafe_code)`） |
| 接受现状 | —— |

### 已实测：并行对这个负载无效

| 线程数 | 1 | 2 | 4 | 8 | 12 |
|---|---|---|---|---|---|
| 1080p×10k 提取 | **0.70–0.91 ms** | 1.02–1.68 | 1.18–1.53 | 1.22–1.69 | 1.27–1.62 |

已排除线程创建开销（实测 304 µs）与分配器争用（主线程预分配无改善）；
同机**纯计算**负载能加速 4.43× —— 机器能并行，是**这个负载**并行不了。

### 结论

**不引入。** 而且事后证明根本不需要：提取的目标是靠
**消除每帧全新分配**达成的（2.03 → 0.59 ms），与并行无关。
详见 `CHANGELOG.md` 的 `[0.3.0-alpha]` 条目。

## ④ 跨厂商硬件验证：放弃（范围收缩）

**原判据**：至少在两个不同厂商的 GPU 上跑通全部测试。
**决定**：放弃 —— 单人开发、手上只有一块显卡，客观上无法执行。

**记录方式**：从"承诺覆盖"改为**「已知未验证项」**。达成的是
**同一块 GPU 上的三个后端**；**跨厂商硬件未验证**。

**为什么必须写明而不是删掉**：这条验证**是有牙齿的** ——
执行它时抓到两个"一换后端就起不来"的真 bug。所以未验证意味着
**可能还存在厂商/驱动相关的未知问题**。写在明处比假装"已验证"好。

将来有第二台机器时，`docs/VERIFY.md` 的清单可直接照着跑。
