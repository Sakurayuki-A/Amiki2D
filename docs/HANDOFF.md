## 规则：不要用 PowerShell 的 `>` 把多行文本写进文件再交给别的工具

**同一类编码坑的第三个变体。**

PowerShell 5.1 的 `>` 重定向**不是 UTF-8**（是 UTF-16LE 或系统代码页）。
于是

```powershell
git tag -l --format='%(contents)' v0.5.0-alpha > tagmsg.tmp   # ✗
git tag -a v0.5.0-alpha -F tagmsg.tmp                          # 标签说明变成 4 字节
```

一个 3.3 KB 的发布说明被写成 4 字节，**而且没有任何一步报错** ——
`git tag -F` 只是照单全收。发现它靠的是事后去读标签对象、数"替换字符"。

**做法**：要交给别的工具的文件，用 `write` 工具写（UTF-8 无 BOM），
不要用 shell 重定向转手。要检查的话，读回来数 `\ufffd`。

**另外**：`git add -A` 之后再 `git tag`，会把当时的临时文件一起提交进去
（本轮 `tag050.tmp` 又中了一次）。**先清理临时文件，再 `git add`**；
发现晚了就 `git rm --cached` + `--amend`，然后**把标签移到新提交上** ——
标签不会自己跟着走。

## 规则：改代码文件时，**读写都必须显式 `encoding="utf-8"`**

**这条是踩了两次才写下来的，第二次代价是毁掉一个 43 KB 的源文件。**

Python 的 `open(path)` **不指定编码时用系统默认**（这台机器是 GBK）。
于是一段看起来无害的代码：

```python
open(P, "w").write(open(P).read().rstrip() + extra)   # ✗✗
```

会 **用 GBK 读 UTF-8 文件、再以 GBK 写回** —— 文件里的中文注释全部损坏，
而且**内容会被截断**（实测 43 KB → 3.4 KB，1202 行删除）。

正确写法，两次都要写：

```python
s = open(P, encoding="utf-8").read()
open(P, "w", encoding="utf-8", newline="").write(s + extra)
```

**为什么危险**：这类损坏**不一定当场报错** —— 它可能仍然是一份"能编译"的文件，
只是内容少了。等发现时往往已经过了好几步。

**防线**：改完之后用 `git diff --stat` 看一眼行数变化。
新增功能时的 deletions 数量应该是**个位数**；出现几百行删除就是出事了，
立刻 `git checkout -- <file>` 恢复。**这也是为什么每轮都要在绿色状态提交。**

## 规则：`.cmd` 与 `.ps1` 一律纯 ASCII

**踩过两次，第二次代价更大。**

- `cmd.exe` 按**系统代码页**（这里是 936）解析 `.cmd` ✗ 中文注释会把脚本撕碎
- PowerShell 5.1 把**无 BOM 的 UTF-8** 当 ANSI 读 ✗ 中文被解码坏之后
  **会吞掉行尾换行**，于是**下一条语句变成注释的一部分** ✗✗

第二次的表现极其隐蔽：`verify.ps1` 里那句取值语句被吞进注释，
`$cargoVer` 变成空字符串，于是版本检查**在版本正确时也报 FAIL** ✗
—— 一个永远失败的检查比没有检查更糟，因为它会被当成"已知噪音"忽略掉。

所以：

1. 这两个扩展名的文件**只写 ASCII**，中文说明放到旁边的 `.md`
2. 写完之后**自检**：`[ (Get-Content f -Raw) -match '[^\x00-\x7F]' ]`
3. **解析失败必须与"值不匹配"区分开** —— 空值说明"没读出来"，
   那是另一类（更严重的）问题，不能伪装成不匹配

## 工作纪律（务必遵守）

1. **绝不给时间估计**。里程碑只按依赖顺序，不说"几天"。
2. **先用最小实验隔离变量，再动代码**。每步只引入一个变量。
   正面教材（本会话）：提取达标卡了很久，连续**实测否定**了四个假说
   （push 慢 / sqrt 慢 / 手工内联 / 移到 GPU），最后用一个对照实验
   （全新分配 0.291 ms vs 复用 0.053 ms）一击定位真因是**每帧缺页**。
   反面教材：在这之前我已经改了两轮"减少 push"的代码 —— 方向全错。
3. **小步验证**：改一处 → `cargo build` → `cargo test --workspace` → 再改下一处。
4. **绝不留"半通"的实现**：宁可显式报错，也不要静默画出错误结果。
   本会话有两次**主动停手**：判定剩余额度不足以安全完成跨侧改动时，
   写下实施方案而不是留下半坏的流水线（其中一次后来证明那方案根本不需要）。
5. **报数字前先确认口径一致**（本会话栽过两次，务必看第 6 条）。
6. **性能数字必须写清测量条件**。本会话的教训：
   - "帧路径 86% 是 GPU 受限" —— 用 `poll` 耗时**推断**的，实测时间戳后是 27–43%
   - "提取已临界达标 798 µs" —— 拿**隔离基准的均值**去对**帧内单次采样**的判据；
     同口径下是 1.023 ms，**未达标**
   - "改 memcpy 省 0.36 ms" —— 机制站不住（实测两者无差别），那 0.36 ms 是噪声
   **报数字前问自己：这个数和判据是同一个口径吗？**
7. **性能断言在测试环境里会失真**（本会话踩了三次）：
   - `cargo test --workspace` **并行**跑同一二进制 → 争用 GPU，
     同一条测试单跑 2.35 ms、并行 5.6–19.7 ms
   - GL 后端走兼容路径 → 20.8 ms，是后端特性不是回归
   - 机器有负载时 `startup_cost` 测出 1598.8 ms，单独复跑 348.4 ms
   处理：性能断言取**多次最小值**，或只做**测量 + 数量级兜底**，
   严格判据交给独立基准。**别去反复调阈值。**
8. 只用编辑工具改文本文件；PowerShell 只用于 cargo 与只读查询。
   **绝对不要**用 `(Get-Content -Raw) -replace ... | Set-Content` 改源码
   （会 GBK 重编码 + LF→CRLF + 破坏字符串续行）。
   本会话用 Python 脚本改源码是可行的，但**注意 Python 字符串里的 `\r`/`\d`
   会被当转义序列** —— 我因此把一行注释写成了含回车符的三行，编译失败。
9. **每关闭一个 B 类（已知限制），同步更新 `docs/OVERVIEW.md` 的能力清单。**
   规则的具体含义：
   - **改了 `KNOWN_ISSUES.md` 里 B 类条目的状态**（例如把 `B5 even-odd 未实现`
     改成已实现）→ 同一批改动里必须动 `OVERVIEW.md` 的
     「二、核心能力」：把它**移进 2.2 的"曾登记为限制、现已关闭"表**（带上编号），
     并从「五、已知限制」里删掉。
   - 反之，**新登记**一条 B 类限制时，`OVERVIEW` 的 `5.2` 也要加一行。
   - **为什么有这条**：`OVERVIEW.md` 曾经整体漂移到 0.3.0 之前的口径
     （0.7.0 已经做到 CJK 禁则 + 字体回退，它还写着"不能排版"），
     根因不是"漏改一处"，而是**能力清单没有和 registry 绑定**：
     `KNOWN_ISSUES` 有稳定编号、会被逐条维护，而 `OVERVIEW` 的能力段落是散文，
     没有对账点。这条规则就是给它们装上对账点。
   - **对账方法**（`OVERVIEW` 里已写死）：把 `KNOWN_ISSUES` 的「已关闭」条目
     （B4 / B5 / B12 / B13 / B15 + 已移出本表的 C4、C3 的一半）与
     `OVERVIEW` 的 2.2 表**逐条对齐**，多写少写都算错。
10. **对账脚本报"不一致"时，先验证脚本本身。**
    具体做法：用 `git show <tag>:<path>` 或更窄的 grep 范围（**限定在目标版本
    的段落内**）复核一遍，确认命中的是**目标段落**而非相邻段落。
    已两次踩"检查器自身出错"：
    - **一次 `$Matches` 覆盖**：连着写两次 `-match`，第二次把第一次的捕获组
      冲掉了，于是"已关闭的 B 类"对出来是空集 ⇒ 报"不一致"。
      做法：**先把捕获组接进变量**，再做第二次匹配。
    - **一次 grep 跨段落命中**：在 `CHANGELOG.md` 里找"输出会变"来判断
      0.9.0 条目有没有写那句提醒，实际命中的是 **0.7.0 段落**里另一句话 ⇒
      误判成"已经写了"。
      做法：**把搜索范围限定到目标版本的段落内**，或用
      `git show <tag>:<path>` 直接看那个版本的文件。
    **为什么有这条**：对账脚本的作用是"用机器代替人眼"，所以它一旦出错，
    就会以"机器说的"这种权威口径误导判断 —— **比没有检查更糟**。
    脚本自身也需要可解释的判据：范围要窄、捕获要接住、必要时回到原始文件核对。

## 逐帧调用必须复用缓冲（重要，别踩）

`build_gpu_scene` / `prepare` / `profile` 每次**新建约 7 MB**。大于 128 KB 的分配
走 `mmap`、释放走 `munmap` → **每帧重新缺页**。实测同一批数据**慢 5.3 倍**。

逐帧路径请用：

| 一次性 | 逐帧 |
|---|---|
| `build_gpu_scene` | `build_gpu_scene_into(scene, eps, &mut gs)` |
| `prepare` | `prepare_into(scene, eps, &mut frame)` |
| `profile` | `profile_into(scene, eps, &mut frame)` |

```rust
let mut frame = amiki_gpu::Frame::default();
loop {
    renderer.prepare_into(&scene, eps, &mut frame)?;   // 缓冲跨帧复用
    renderer.render_into(&tex, &frame)?;
}
```

## 为什么交接里强调那几条纪律

那几条不是套话，**每一条都是踩出来的**：

| 纪律 | 对应的事故 |
|---|---|
| 最小实验隔离变量 | GPU 滤镜卡很久，最后 4 步探针定位；提取达标前连错四个方向 |
| 小步验证 | 投机分配那次一次性大改，文件损坏只能回退 |
| 不留半通实现 | GPU 滤镜曾"半通"，会静默画出与 CPU 不一致的结果 |
| 消息指向正确方向 | 3 次误导性消息，每次浪费一轮排查 |
| 不用 PowerShell 改源码 | 早期事故：GBK 重编码 + 破坏字符串续行 |
| **口径一致** | 本会话两次用自己的错误结论去对判据（86% GPU / 临界达标） |
| **性能断言的环境失真** | 本会话三次假失败，每次都在调阈值上浪费时间 |
