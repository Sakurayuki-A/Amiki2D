# Amiki2D 第一个发布版本计划（0.3.0）

> 本文回答一个问题：**第一个不带 `alpha` 后缀的版本，必须完成什么。**
>
> 不含时间估计（本项目只按依赖顺序推进，不给工期）。

---

## 一、发布目标

**一个"能画出完整界面、且在真实 UI 上兑现核心卖点"的版本。**

这句话有两个重点，各自对应一类门槛：

| 重点 | 含义 | 对应门槛 |
|---|---|---|
| **能画出完整界面** | 通用 2D 图元齐备 | 缺**描边** → 不能称通用 |
| **在真实 UI 上兑现核心卖点** | 增量渲染在**有滤镜的界面**上仍然有效 | 缺它 → 卖点在真实场景里失效 |

### 为什么是 0.3.0 而不是 1.0.0

- `0.3.0`：功能完备、可用于真实项目，但**不承诺 API 稳定**
- `1.0.0`：在 0.3.0 之上再加 **API 冻结**与**足够时长的 dogfooding**

先定 0.3.0，1.0.0 的判据见第五节。

---

## 二、P0 —— 能力门槛（缺了不能发布）

### P0-1 描边（stroke）

**为什么是门槛**：只有填充的 2D 渲染器画不出边框、图标轮廓、折线图、文字装饰。这是当前最大的能力空洞。

**范围**：
- join：`miter` / `round` / `bevel`，含 `miter_limit`
- cap：`butt` / `round` / `square`
- 闭合与开放路径
- 与填充一致的 paint 支持（纯色 / 渐变 / 位图）

**技术难点（必须先解决，否则会走弯路）**：

本项目用**解析式覆盖率**（每像素闭式线积分）做抗锯齿。描边的难点不是"怎么画粗线"，而是**重叠部分不能重复计入覆盖率**：

- 若把描边拆成"每段一个四边形 + join/cap 图形"，**相邻段在转角处必然重叠**，逐块积分再相加会**把 alpha 叠高**（半透明描边会出现深斑）
- 若先把路径偏移成单一闭合轮廓再填充，则要做**曲线偏移**（cubic 偏移不是 cubic，且 miter join 会截断）

**建议方向**：把描边表达为**有符号距离场意义上的"到路径距离 ≤ 半宽"**，而覆盖率积分直接对这个区域做 —— 即把"描边区域"看成若干**互斥分块**（按段的中点界划分转角归属），使每像素最多落入一个分块。这需要为"到线段的距离"推导闭式积分，而不是复用填充的积分。

**验收标准**：
- 与 CPU 参考实现对拍，最大通道差 ≤ 2/255
- 半透明宽描边在自交/急转角处**不出现深斑**（这是上面那个难点的直接检验）
- 任意缩放不糊（沿用解析覆盖率的既有性质）
- 与 Skia / Cairo 同场景目视对比无可见差异

### P0-2 含层场景的增量渲染 —— ✅ **已完成**

> 修掉了两个**静默错误**：`PersistentRenderer` 的增量分支从不合成层；
> `edit_damage` 完全忽略 `layers`（层内改动产生零脏区）。两者合起来是
> "有滤镜的界面从第二帧起悄悄丢掉滤镜"。
>
> 修法是三个缓冲分工：`base`（仅图元）/ `image`（最终）/ `layers`（已滤波缓冲缓存）；
> 脏 tile 上 `image ← base` 再按序叠层。全量与增量**共用**同一份层数学
> （`layer_buffer_from_content` + `blend_layer_rect`），不会漂移。
>
> 实测：带投影的静态界面 **3.5% tile 重画（省 96.5%）**，此前是 100%。
> 测试含 60 轮含层随机编辑序列与全量逐字节对拍。


**为什么是门槛**：M4 的 damage region 是核心卖点（静态界面省 96.5% tile 着色）。但**真实 UI 几乎都有阴影或模糊**，而当前 `render_damage` 一检测到层就**回落全量渲染** —— 等于卖点在真实场景里归零。

**当前状态**：

```
无层场景：静态界面省 96.5% tile 着色   ✅
有层场景：回落全量渲染，省 0%          ❌
```

**难点**：层合成需要把整层渲染到离屏纹理再读回，这与 damage 的"少读回、少重绘"直接冲突。

**建议方向**（三件事，按顺序）：
1. **层内也用 damage**：层有自己的脏区，只重绘层内的脏 tile
2. **层纹理跨帧复用**：层内容未变时**不重模糊**（模糊是层里最贵的一步）
3. **damage 传播**：层内容变化 → 层脏区 → 模糊膨胀（用已有的 `inflated_bounds`）→ 合成到主画布的脏区

**验收标准**：
- 一个**带阴影的静态界面**，连续帧的 tile 重画率 **< 10%**（当前 100%）
- 带模糊层的界面在只有局部变化时，重画率同样 < 10%
- 增量路径与全量路径**逐字节一致**（沿用 M4 已有的随机序列一致性证明方式）
- 层内容变化时，模糊半径内的**主画布** tile 必须全部标脏（否则会出现残影）

### P0-3 解掉逐帧路径对层的拒绝 —— 🔶 **部分完成**

> **已做**：GPU 帧路径不再对含层场景整体报错，而是**在 GPU 上直接合成**（compute
> pass，不读回）。`Filter::None` 与 `Blur` 与参考**逐像素一致**（差 0 / 1），
> 覆盖 `render_into` 与 `render_into_persistent` 两条入口。
>
> **未做**：`Filter::DropShadow` 在帧路径上仍**显式报错**。差异已定位到"阴影放置
> 偏移在 GPU 侧未生效"这一层，但未确认到底；**在无法确认正确性之前不启用**。
>
> 过程中找到并修掉了 `inflate_by_filter` 的一个**真 bug**（DropShadow 的作用范围
> 把原点也平移了 `dx`，是平移而非并集 → 正偏移时裁掉左边/上边；CPU 与 GPU 共用
> 这个函数，两端一起受益）。
>
> **判定**：本项**未达验收标准**（"含层场景能走逐帧持久化路径"目前只对
> None/Blur 成立）。按计划允许的退路，限制是**显式**的（运行时报错 + 错误信息
> 指明 DropShadow），不是静默错误。


**为什么是门槛**：当前 `render_into` / `render_into_persistent` 对含层场景**显式报错**。作为正式版本，"某些场景不能走主路径"是个不该有的限制。

**说明**：P0-2 做完后这一项**大概率自然解决** —— 层的离屏纹理一旦跨帧复用，逐帧路径就不需要额外读回。若届时仍有冲突，则退而求其次：把它明确定义为"无层场景的快速路径"，并在**类型层面**（而非运行时报错）表达这个限制。

**验收标准**：含层场景能走逐帧持久化路径；或该限制在**类型系统**里，编译期就挡住。

## 三、P1 —— 性能门槛

### P1-1 CPU 提取的 SIMD 与多线程（M7 的性能项）

**为什么是门槛**：帧路径 1080p×10k 是 **10.00 ms**，其中 GPU 只占 **2.83 ms** —— 墙钟是 GPU 的 3.5 倍，而差距主要在 **`提取` 2.03 ms（纯 CPU）** 与上传。

**范围**：
- 提取阶段（变换 + 控制点 + 闭式段数）向量化（AVX2 / NEON）
- 按 draw 分块多线程提取

**验收标准**：
- 1080p×10k 的 `提取` 从 **2.03 ms → < 0.8 ms**
- 帧路径总墙钟 **10.00 ms → < 6 ms**（GPU 2.83 + 开销）
- 多线程结果与单线程**逐字节一致**
- 在无 SIMD 支持的平台上有标量回退路径

> 注：M7 定义里的 **C ABI / WASM / HDR 不在本版范围**（见第六节）。

## 四、P2 —— 文本完备性

### P2-1 CJK 断行验证

**为什么是门槛**：断行逻辑写了，但**仓库只有 Inter（无汉字）**，测试只断言"不 panic"。**未验证**不等于"能用"。

**范围**：
- 引入一份 OFL 的 CJK 字体（Noto Sans CJK 之类）到 `assets/fonts/`
- **禁则处理**：标点不能出现在行首（`、。，」』）` 等），开引号不能出现在行尾
- CJK 与拉丁混排的断行

**验收标准**：
- 中文段落断行**不出现标点行首**（逐个断言，而非"不 panic"）
- 混排段落的断行点符合预期（有具体测试用例）
- 字体许可文件随仓库分发

### P2-2 字距（kerning）

**为什么是门槛**：rustybuzz 已在依赖里，`kern` 特性结果是可取的 —— 拿不到是**遗漏**而非"不支持"。TeX 级别的排版质量依赖它。

**验收标准**：`AV`、`To` 等经典字距对的位置与 HarfBuzz 参考输出一致。

## 五、P3 —— 工程成熟度（发布前的"可信度"）

这些不是功能，但决定"能不能放心用"。

| 项 | 当前问题 | 验收标准 |
|---|---|---|
| **多适配器验证** | 只在 RTX 3050 上跑过 | 至少在**两个不同厂商**的 GPU（或独显+核显）上跑通全部测试 |
| **启动开销** | `GpuRenderer::new()` 0.5–0.7 s（21 条管线，无 PipelineCache） | < 200 ms（PipelineCache 或惰性创建） |
| **文件规模** | `amiki-gpu/src/lib.rs` **5796 行**（单文件过半万） | 拆为 pipeline / sparse / layer / profile / tests 等模块 |
| **API 稳定性** | 未声明哪些是稳定接口 | 一份 `pub` 面清单；内部项标 `#[doc(hidden)]` |
| **dogfooding** | 只跑示例，没用它构建过完整应用 | 一个真实窗口应用（滚动 + 交互 + 文字），持续跑通 |
| **文档同步** | 已有 CHANGELOG/OVERVIEW/ARCHITECTURE/HANDOFF | 全部与代码一致；补一份"能力与限制"清单 |

## 六、明确**不做**（避免范围蔓延）

| 项 | 为什么推迟 |
|---|---|
| **双向文本**（阿拉伯/希伯来） | 面向特定语言；需要独立的 bidi 算法 + 字形重排序 |
| **Knuth-Plass 全局最优断行** | 排版质量提升，不是能力缺失；贪心断行已可用 |
| **HDR / 宽色域** | 色彩能力扩展，与"通用 2D"正交 |
| **C ABI / WASM** | **分发形式**，不是能力。除非确定要跨语言/浏览器调用，否则不做 |
| **图像缩放 mipmap** | 缩小质量；当前双线性已可用 |
| **新的混合模式 / 滤镜 / 渐变类型** | 现有 16 混合 + 模糊/投影 + 三渐变类型已够用 |
| **动画系统** | 那是渲染器之上的层，不属于本项目 |

> **需要你决定的一项**：C ABI / WASM 是否纳入。判据是**这个版本以什么形式被使用** ——
> 给 Rust 项目当库用 → 不做；给别的语言或浏览器调用 → 必须做，且是硬门槛。

                          │（与其它项独立，可并行）

## 八、发布判据（全部满足才算完成）

1. P0-1 / P0-2 / P0-3 / P1-1 / P2-1 / P2-2 全部达成各自验收标准
2. P3 各项达成
3. **没有已知的静默错误路径** —— 任何不支持的能力都必须**显式报错**，不能悄悄画错
4. 全部测试通过，且新增能力都有**与 CPU 参考实现的对拍**或**一致性证明**
5. 文档与代码一致；CHANGELOG 记录全部已修缺陷
6. 一个真实应用可持续运行

## 八点五、已知的未复现问题（要盯住）

**一次不可复现的测试瞬时失败**（`cargo test --workspace`）：

- 出现时间：P0-1 描边完成后的验证运行
- 现象：`amiki-gpu --lib` 报 `error: test failed`，但日志里**没有留下 panic 信息**
  （PowerShell 把 `*>` 与 `2>&1` 混用，输出交错丢失）
- 之后连续 **8 次**运行（5 次单跑 `amiki-gpu --lib` + 3 次 `--workspace`）**全部通过**，
  合计 119 条，无法复现

可疑方向（未证实）：`cargo test --workspace` 会**并行运行不同 crate 的测试二进制**，
而 `amiki`（门面测试）与 `amiki-gpu` 的测试都会各自创建 GPU 设备 —— 并发创建设备
可能争用。

**为什么现在不修**：无法复现就没有可验证的修复。先记录在此；
若再出现，第一件事是**用可靠的方式捕获 panic 信息**
（把输出重定向到文件并单独取 `cargo test` 的 stderr，而不是在 PowerShell 里混流）。

## 九、主要风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **描边的解析覆盖率** | 重叠不重复计数是数学问题，不是工程问题；可能推翻"拆成图元"的做法 | 先用最小实验证明"单段粗线"的闭式积分，再处理 join；**不要一次做完** |
| **层的 damage 传播** | 模糊半径会使脏区膨胀，漏标一处就出残影（难发现） | 用**随机编辑序列**的一致性证明（M4 已有此方法），而不是手写几个用例 |
| **多线程与确定性** | 并行提取若改变浮点累加顺序，会破坏"与 CPU 逐字节一致" | 并行只做**分块**（每块内部仍串行），块间结果按固定顺序归并 |
| **CJK 断行的范围蔓延** | 禁则处理与断行规则可无限细化 | 只做**硬性禁则**（标点行首/行尾），不做完整的 JIS/GB 断行等级 |

## 十、与既有里程碑的关系

| 里程碑 | 本版是否包含 |
|---|---|
| M1–M3、M3.5 | 已完成 |
| M3.6 | **P1-1 补完**（剩余项依赖 M7 的 CPU 优化，正是本版的 P1-1） |
| M4 | **P0-2 补完**（当前在有层场景失效） |
| M5 | **P2-1 / P2-2 补完**（CJK 未验证、字距遗漏） |
| M6 | 已完成 |
| M7 | **只取性能项**；C ABI / WASM / HDR 推迟 |

**结论**：0.3.0 = 把已完成的 M4 / M5 / M6 在**真实场景**下补齐，加上缺失的基本图元（描边）与性能收尾。
