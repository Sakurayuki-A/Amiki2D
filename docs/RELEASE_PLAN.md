# Amiki2D 第一个发布版本计划（0.3.0）

> 本文回答一个问题：**第一个不带 `alpha` 后缀的版本，必须完成什么。**
>
> 不含时间估计（本项目只按依赖顺序推进，不给工期）。

---

## 一、发布目标

**一个"能画出完整界面、且在真实 UI 上兑现核心卖点"的版本。**

这句话有两个重点，各自对应一类门槛：

| 重点 | 含义 | 对应门槛 |
|---|---|---|
| **能画出完整界面** | 通用 2D 图元齐备 | 缺**描边** → 不能称通用 |
| **在真实 UI 上兑现核心卖点** | 增量渲染在**有滤镜的界面**上仍然有效 | 缺它 → 卖点在真实场景里失效 |

### 为什么是 0.3.0 而不是 1.0.0

- `0.3.0`：功能完备、可用于真实项目，但**不承诺 API 稳定**
- `1.0.0`：在 0.3.0 之上再加 **API 冻结**与**足够时长的 dogfooding**

先定 0.3.0，1.0.0 的判据见第五节。

## 二、P0 —— 能力门槛（缺了不能发布）

### P0-1 描边（stroke）

**为什么是门槛**：只有填充的 2D 渲染器画不出边框、图标轮廓、折线图、文字装饰。这是当前最大的能力空洞。

**范围**：
- join：`miter` / `round` / `bevel`，含 `miter_limit`
- cap：`butt` / `round` / `square`
- 闭合与开放路径
- 与填充一致的 paint 支持（纯色 / 渐变 / 位图）

**技术难点（必须先解决，否则会走弯路）**：

本项目用**解析式覆盖率**（每像素闭式线积分）做抗锯齿。描边的难点不是"怎么画粗线"，而是**重叠部分不能重复计入覆盖率**：

- 若把描边拆成"每段一个四边形 + join/cap 图形"，**相邻段在转角处必然重叠**，逐块积分再相加会**把 alpha 叠高**（半透明描边会出现深斑）
- 若先把路径偏移成单一闭合轮廓再填充，则要做**曲线偏移**（cubic 偏移不是 cubic，且 miter join 会截断）

**建议方向**：把描边表达为**有符号距离场意义上的"到路径距离 ≤ 半宽"**，而覆盖率积分直接对这个区域做 —— 即把"描边区域"看成若干**互斥分块**（按段的中点界划分转角归属），使每像素最多落入一个分块。这需要为"到线段的距离"推导闭式积分，而不是复用填充的积分。

**验收标准**：
- 与 CPU 参考实现对拍，最大通道差 ≤ 2/255
- 半透明宽描边在自交/急转角处**不出现深斑**（这是上面那个难点的直接检验）
- 任意缩放不糊（沿用解析覆盖率的既有性质）
- 与 Skia / Cairo 同场景目视对比无可见差异

### P0-2 含层场景的增量渲染 —— ✅ **已完成**

> 修掉了两个**静默错误**：`PersistentRenderer` 的增量分支从不合成层；
> `edit_damage` 完全忽略 `layers`（层内改动产生零脏区）。两者合起来是
> "有滤镜的界面从第二帧起悄悄丢掉滤镜"。
>
> 修法是三个缓冲分工：`base`（仅图元）/ `image`（最终）/ `layers`（已滤波缓冲缓存）；
> 脏 tile 上 `image ← base` 再按序叠层。全量与增量**共用**同一份层数学
> （`layer_buffer_from_content` + `blend_layer_rect`），不会漂移。
>
> 实测：带投影的静态界面 **3.5% tile 重画（省 96.5%）**，此前是 100%。
> 测试含 60 轮含层随机编辑序列与全量逐字节对拍。


**为什么是门槛**：M4 的 damage region 是核心卖点（静态界面省 96.5% tile 着色）。但**真实 UI 几乎都有阴影或模糊**，而当前 `render_damage` 一检测到层就**回落全量渲染** —— 等于卖点在真实场景里归零。

**当前状态**：

```
无层场景：静态界面省 96.5% tile 着色   ✅
有层场景：回落全量渲染，省 0%          ❌
```

**难点**：层合成需要把整层渲染到离屏纹理再读回，这与 damage 的"少读回、少重绘"直接冲突。

**建议方向**（三件事，按顺序）：
1. **层内也用 damage**：层有自己的脏区，只重绘层内的脏 tile
2. **层纹理跨帧复用**：层内容未变时**不重模糊**（模糊是层里最贵的一步）
3. **damage 传播**：层内容变化 → 层脏区 → 模糊膨胀（用已有的 `inflated_bounds`）→ 合成到主画布的脏区

**验收标准**：
- 一个**带阴影的静态界面**，连续帧的 tile 重画率 **< 10%**（当前 100%）
- 带模糊层的界面在只有局部变化时，重画率同样 < 10%
- 增量路径与全量路径**逐字节一致**（沿用 M4 已有的随机序列一致性证明方式）
- 层内容变化时，模糊半径内的**主画布** tile 必须全部标脏（否则会出现残影）

### P0-3 解掉逐帧路径对层的拒绝 —— ✅ **已完成**

> GPU 帧路径不再对含层场景报错，改为**在 GPU 上直接合成**（compute pass，不读回）。
> 三种滤镜 × 两条入口全部与参考一致：
>
> | 滤镜 | 与 `render_blocking` | 与 CPU | 帧持久路径 |
> |---|---|---|---|
> | `None`（分组） | 0 | 0 | 0 |
> | `Blur` | 1 | 1 | 1 |
> | `DropShadow` | 1 | 1 | 1 |
> | `DropShadow`（sigma=0） | 0 | 0 | 0 |
>
> **关键决定**：用 compute 而不是 render pass —— 调用方提供的输出纹理只有
> `STORAGE_BINDING | TEXTURE_BINDING | COPY_SRC`，没有 `RENDER_ATTACHMENT`
> 也没有 `COPY_DST`；compute 能写 storage texture，也只需要已有的 `COPY_SRC`
> 就能先把目标拷进 backdrop（W3C 混合需要背板）。
>
> 过程中修掉四个缺陷（含一个 **CPU/GPU 共用**的真 bug：`inflate_by_filter` 对
> DropShadow 把原点也平移了 `dx`，是平移而非并集 → 正偏移时裁掉左边/上边），
> 以及一个**参数传反**（`layer_tex` 与 `shadow_tex`）—— 后者只跟 `render_blocking`
> 对比会被漏掉，必须同时跟 CPU 对比才暴露。

## 三、P1 —— 性能门槛

### P1-1 CPU 提取的 SIMD 与多线程（M7 的性能项）—— 🔶 **部分完成**

**为什么是门槛**：帧路径 1080p×10k 是 10.00 ms，其中 GPU 只占 2.83 ms ——
墙钟是 GPU 的 3.5 倍，而差距主要在 **`提取` 2.03 ms（纯 CPU）** 与上传。

**已做**：
- 给 `cpu_extract` 基准补上 **1080p×10k** 用例（此前只有 720p×64 与 1080p×1000，
  而本项关心的正是 10k）
- 提取路径改为 `DrawPrims` + **容量预留**（10k 条 draw 不再反复扩容）

**实测**：

| 场景 | 改前 | 改后 |
|---|---|---|
| 帧路径 720p×64 | 486 µs | 487 µs |
| 帧路径 1080p×10k | 9.93 ms | **9.34 ms**（−6%） |
| 提取（隔离基准，10k） | — | **≈940 µs** |

**被实测否定的一次尝试：每帧起线程。**
逐 draw 的提取互不依赖，我实现了一版"分块 + 按序合并"（顺序固定，结果与串行
**逐字节一致**），并设阈值避免小场景被拖累。**实测是净损失**：

| 场景 | 串行 | 每帧起线程 |
|---|---|---|
| 1080p×10k | **942 µs** | 1346 µs |
| 1080p×1000 | **60 µs** | 370 µs |

固定开销约 **1.2 ms** —— `std::thread::scope` 每帧创建/回收线程的成本，
而 `build_gpu_scene` 是**逐帧**调用的。**已按实测撤掉并行**，
并在代码里写明正确做法是**常驻线程池**（本项目刻意不引入 `rayon`，
需要一个基于 `std::sync::mpsc` 的小池子）。

**未达标**：当前 **940 µs / 9.34 ms**，判据是 `< 0.8 ms / < 6 ms`。
差的部分**不是算法问题，是缺一个常驻线程池**。

> **测量教训**：同一份串行算法在隔离基准里是 940 µs，在帧内的 `提取` 分段里
> 报 2.0–2.4 ms（与 GPU 工作交替执行、争用内存带宽）。
> **隔离基准给的是下界，帧内数字才是真实成本。**
> 另：有一次测到 1278 µs，复测三次都是 925–966 —— 是负载导致的离群值，
> **单次测量不足以下结论**。

### P2-2 字距（kerning）—— ✅ **已完成**（并修掉一个相关真 bug）

**两个发现**：

**一、shaping 的字距本来就是生效的。** `shape` 累加的是 rustybuzz 的
`x_advance`，默认包含 GPOS 字距。实测 Inter 的 `AV`：V 的起点从
0.6899 em 收到 0.6216 em（**收紧 0.0684 em ≈ 7%**）。
所以"拿不到是遗漏"的猜测不成立 —— 缺的是**验证**。已补两条测试：
`kerning_is_applied`（AV 必须收紧）与 `non_kerned_pair_is_not_tightened`
（HH 不得收紧）。第二条是必要的对照，否则第一条可能只是"任何两字都被收紧了"。

**二、排版压根没用 shaping 的宽度（真 bug）。** `measure_chars` 逐字符累加
`font.advance_width(c)` —— 那是**不做 shaping** 的宽度，**既没有字距也没有连字**；
而同一文件里的 `measure_run`（断行后测行宽）用的却是 shaping 结果。
于是**排版宽度 ≠ 渲染宽度**：断行偏保守、`LayoutResult::size` 与画面也对不上。

**修法**：给 `amiki-text` 加 `shape_clustered`（返回字形及其 `cluster` 字节偏移），
排版据此把推进量映射回字符边界：

- 整段 shaping 一次（不是每个前缀各 shaping 一次，那是 O(n²)）
- 连字会让多个字符落在同一 cluster → 它们的前缀宽度相同（连字不可拆）
- shaping 失败时**回退并打印说明**，不静默给出不同结果

实测：单行 `AV` 的行宽 **131.15**（逐字符累加会得到 137.99），
与渲染宽度一致到 0.05 px 以内。

> **我自己踩的坑**：第一版测试把 `run.glyphs[i].x`（**em 单位**，字号在渲染时
> 才乘）与 `advance_width(...) * size`（**设备像素**）直接比较，断言写成
> "V 应从 74.32 收到 0.62" —— 看起来很荒谬，实际是单位错了，代码没问题。
> 已把单位写进注释。

### 多适配器验证的实质发现

**一、DX12 原本根本跑不起来 —— "一套 WGSL 通吃"当时是假的。**
`Backends::DX12` 下 `create_shader_module` 直接失败：

```
FXC D3DCompile error: amiki_fine(…): error X3511:
forced to unroll loop, but unrolling failed.
```

根因在**我们自己的 WGSL**：FXC 看到常量次数的循环会尝试展开以把下标静态化，
而下标依赖运行期值。三处这种写法：`int_clamped_linear` 的排序网络
（`ij[st]`、`ts[p.x]`）、`blend_color` 的 case 6/7/9（`o[i]`，**这处才是真正
报错的**）。全部显式展开后编译通过，且**数值逐位相同**（比较交换顺序未变）。

**二、GL 的着色器编译失败（一个字符）。** naga 生成的 GLSL 是
`textureSize(sampler2D, uint)`，驱动要 `int` —— 来源是我们 4 处
`textureLoad(clip_texN, gid, 0u)`。把 mip 层参数写成 `0`（i32）即可：
GL 从 **12 条失败**降到 **1 条**。

**三、GL 的位图读不出来 → 改为显式拒绝。**
现象归一：经采样器得 `(0,0,0,1)`（**GL 规范对"不完整纹理"的规定返回值**），
直接 `textureLoad` 得 `(0,0,0,0)` —— 该数组纹理在 GL 上是空的。
已排除：LOD 钳位、`textureSampleLevel` vs `textureSampleGrad`、辅助函数内联、
`write_texture` 行距 256 对齐、手工双线性（全部实测无效）。
判断是 wgpu/naga 的 GL 后端在 `texture_2d_array` 上的问题。
**按本项目一贯约定，不支持就显式报错，不静默画错。**

> **测量教训**：中途我从"最差像素从 (39,8) 移到 (8,8)、最大差 255→250"
> 推断 `textureLoad` 能取到数据。**这个推断是错的** —— 250 是测试场景垫底的
> 背景色 `rgb8(250,250,250)`，即"位图完全没有贡献"。
> **只看差值大小不足以判断，必须看实际值。**

### 启动开销：定位结论推翻了本计划原先的假设

分段实测：**`Instance` + 请求适配器占 86%**（默认配置 294.6 ms 冷），
而**全部 21 条管线只占 12.7 ms**。所以本计划原先写的
"用 PipelineCache / 惰性创建"**是错的** —— 那样最多省 13 ms。

| 配置 | 冷 | 热 |
|---|---|---|
| 默认（全部后端 → 本机选 Vulkan） | 337 ms | 202 ms |
| `AMIKI_BACKENDS=vulkan` | **154 ms** | 53 ms |
| `AMIKI_BACKENDS=dx12` | 2272 ms | 2093 ms |

DX12 慢是 FXC **运行期编译**着色器的固有代价。现代 DXC 会快得多，但
`wgpu` 的 `static-dxc` 特性依赖 `mach-dxcompiler-rs`，**在构建期用 curl 下载 DLL**
—— 与项目"保持依赖轻量"冲突（离线构建会失败），**不采用**。

**默认保持全部后端**：默认值要保证"哪台机器都能起来"，指定单一后端会削弱
"一套 WGSL 通吃"。（我一度把默认改成只用 Vulkan，快一倍，已按此理由改回。）
需要更快启动的应用可显式指定后端，或利用 `new()` 本就是 `async`、与窗口初始化重叠。

## 六、明确**不做**（避免范围蔓延）

| 项 | 为什么推迟 |
|---|---|
| **双向文本**（阿拉伯/希伯来） | 面向特定语言；需要独立的 bidi 算法 + 字形重排序 |
| **Knuth-Plass 全局最优断行** | 排版质量提升，不是能力缺失；贪心断行已可用 |
| **HDR / 宽色域** | 色彩能力扩展，与"通用 2D"正交 |
| **C ABI / WASM** | **分发形式**，不是能力。除非确定要跨语言/浏览器调用，否则不做 |
| **图像缩放 mipmap** | 缩小质量；当前双线性已可用 |
| **新的混合模式 / 滤镜 / 渐变类型** | 现有 16 混合 + 模糊/投影 + 三渐变类型已够用 |
| **动画系统** | 那是渲染器之上的层，不属于本项目 |

> **需要你决定的一项**：C ABI / WASM 是否纳入。判据是**这个版本以什么形式被使用** ——
> 给 Rust 项目当库用 → 不做；给别的语言或浏览器调用 → 必须做，且是硬门槛。

  合计 119 条，无法复现

而 `amiki`（门面测试）与 `amiki-gpu` 的测试都会各自创建 GPU 设备 —— 并发创建设备
可能争用。

**为什么现在不修**：无法复现就没有可验证的修复。先记录在此；
若再出现，第一件事是**用可靠的方式捕获 panic 信息**
（把输出重定向到文件并单独取 `cargo test` 的 stderr，而不是在 PowerShell 里混流）。

## 九、主要风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **描边的解析覆盖率** | 重叠不重复计数是数学问题，不是工程问题；可能推翻"拆成图元"的做法 | 先用最小实验证明"单段粗线"的闭式积分，再处理 join；**不要一次做完** |
| **层的 damage 传播** | 模糊半径会使脏区膨胀，漏标一处就出残影（难发现） | 用**随机编辑序列**的一致性证明（M4 已有此方法），而不是手写几个用例 |
| **多线程与确定性** | 并行提取若改变浮点累加顺序，会破坏"与 CPU 逐字节一致" | 并行只做**分块**（每块内部仍串行），块间结果按固定顺序归并 |
| **CJK 断行的范围蔓延** | 禁则处理与断行规则可无限细化 | 只做**硬性禁则**（标点行首/行尾），不做完整的 JIS/GB 断行等级 |

## 十、与既有里程碑的关系

| 里程碑 | 本版是否包含 |
|---|---|
| M1–M3、M3.5 | 已完成 |
| M3.6 | **P1-1 补完**（剩余项依赖 M7 的 CPU 优化，正是本版的 P1-1） |
| M4 | **P0-2 补完**（当前在有层场景失效） |
| M5 | **P2-1 / P2-2 补完**（CJK 未验证、字距遗漏） |
| M6 | 已完成 |
| M7 | **只取性能项**；C ABI / WASM / HDR 推迟 |

**结论**：0.3.0 = 把已完成的 M4 / M5 / M6 在**真实场景**下补齐，加上缺失的基本图元（描边）与性能收尾。
