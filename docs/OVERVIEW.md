## 一、一句话

**Amiki2D 现在能渲染图形，但还不会渲染界面。**

已经会画：矩形、圆、任意贝塞尔曲线、自相交多边形、16 种混合模式、裁剪合成，
抗锯齿是**数学精确**的（不是采样估计），而且**特别省显存**。

还不会画：**文字、描边、渐变、图片、模糊**。

所以它现在**还不能用来做 UI、文档、图表**这类真正需要 2D 引擎的东西。
用一句话概括：**发动机造好了，方向盘和座椅还没装。**

---

## 二、它到底想成为什么

不是"又一个 Skia"。它想在**通用引擎**的前提下，拿回一件现有引擎普遍放弃的东西：

> **把「画布面积」从资源预算里去掉。**

主流引擎（Skia / Direct2D / Blend2D）的中间数据都与**画布面积**成正比：
4K 画布上什么也没有，照样占内存、照样烧带宽。

Amiki2D 让资源占用只随**画面实际内容**增长：

| 场景 | 传统做法 | Amiki2D |
|---|---|---|
| 1080p，一万条曲线 | 20.93 GB（根本跑不了） | **34.5 MB** |
| 空画布 | 与画布等面积的开销 | **零分配** |

换成用户能感知的话：**让「画一万个元素」和「画十个元素」在内存与重绘成本上是一个量级。**

这对带文本和图表的界面、文档查看器、地图、数据可视化是决定性的。

### 一个必须承认的边界

这个设计**偏向"静态或缓变的、内容量大的"画面**（UI、图表、文档）。
对"整屏每帧全变"的场景（全屏游戏特效、视频播放），稀疏结构的开销反而**比传统渲染器更重**。

所以真正的差异化不是"我们更快"，而是：

> **在其他引擎里空间和时间都随画布走的场合，我们让它们随内容走。**

## 四、这次对话做了什么（为什么"看不出变化"）

这次做的**全部是"看画面看不出来"的工作**。这不是没干活——这些工作本来就是
**不该改变画面**的那一类，每次都特意验证过"输出逐字节不变"。

用一个比方：

| 做的事 | 打比方 |
|---|---|
| **M3.5** 工程硬化 | 装**验收用的检测设备和规矩** |
| **M3.6** 读回池化 | 拆掉一条**瓶颈管道** |
| **M4** damage 起步 | 打好**增量施工的基础** |

### M3.5：装了检测设备（已完成）

**问题**：以前如果渲染数学被改错，而且 GPU 和 CPU 两边**同时**改错，
现有测试会**通过**，bug 静默留下。历史上真的发生过一次（CPU 用自适应压平、
GPU 用均匀压平，两边不一致但很难发现）。

**现在**：加了两层独立的检查——
- **自洽检查**：不依赖任何"参照实现"，直接检查 GPU 内部数据结构是否自相矛盾
- **输出快照**：把 8 个场景的渲染结果用哈希钉死，任何非预期变化立刻失败

我实测过：故意改错一行，它立刻指出错在哪个场景、哪个单元。

### M3.6：拆了一条 85% 的瓶颈（部分完成）

**问题**：帧时间几乎全花在"从 GPU 取回数据"上（占 21.9 ms 里的 20 ms），
而且每次取回都新建一个缓冲、做一次冷映射。

**现在**：改成复用缓冲。实测 **720p 帧时间 6.59 ms → 1.03 ms（−85%）**。

### M4：增量渲染的地基（进行中）

**目标**：从"每帧把整个画面重画一遍"变成"**只重画改动过的地方**"。

**已完成**：
- **脏区模型**：能表达"整幅全脏 / 部分脏 / 干净"三种状态，并量化到 tile 粒度
- **CPU 增量渲染**：只重算脏 tile，其余复用上一帧结果
- **正确性证明**：用 **200 轮随机改动的测试**验证"增量结果与全量渲染逐字节一致"
  （这是我特意用随机而非样例的原因——增量渲染最典型的 bug 是"特定序列下才错"，
  样例测试抓不住）

**还没做**：让渲染器**跨帧记住上一帧**。现在每次仍从零开始，
所以增量的收益还没真正到手上。

## 六、接下来做什么，以及为什么是这个顺序

### 第 1 步：帧间持久化（让增量真正生效）

现在"只重画脏区"的能力已经证明是对的，但**没人记住上一帧**。
接上之后，**静态画面从"每帧全画"变成"几乎不画"**。

这是**第一个你能感觉到速度的改动**，但画面依然不变。

### 第 2 步：文字 ← 第一个能看出区别的改动

做完它，Amiki2D 才真的算"通用 2D 引擎"，才能渲染界面、文档、图表。

**为什么放在持久化之后**：文字的核心难点是字形轮廓要被成千上万次复用，
需要缓存；而缓存的价值取决于"静态内容不重算"——这正是持久化提供的能力。
顺序反了，缓存做了也白做。

而且这条路有个漂亮的兑现方式：字形轮廓**直接走解析覆盖率管线**，
所以**任意缩放都不糊**，不像传统方案那样依赖预渲染的字形位图。
这个主张会做成**可测的判据**（多个缩放级别下与超采样参照比对），不是宣传语。

### 第 3 步：渐变 / 图片 / 滤镜

界面美化需要的东西。做完就能画出像样的 UI 了。
结构上依赖一个"层树"（离屏合成），所以放在文字之后。

### 暂时不做，以及为什么

| 不做 | 原因 |
|---|---|
| CPU 引擎 SIMD / 多线程 | 当前瓶颈在"重算量"而非"CPU 算力"，先解决重算量 |
| 管线缓存（启动 0.5–0.7 s） | 只影响离屏一次性出图，不影响实时帧路径 |
| C ABI / WASM / HDR | 等有内容能力后再谈生态，现在做等于包装一个不能用的东西 |

## 七、怎么自己看进度（不用读我的叙述）

```bash
cargo run --release -p amiki --example headless_png   # 出一张图：看它现在能画什么
cargo run --release -p amiki --example window_demo     # 打开动画窗口
cargo test  --workspace                                # 45 个测试
cargo bench -p amiki-gpu                               # 性能数据（含逐 pass 明细）

git log --oneline                                      # 开发时间线
```

**最诚实的进度说明就是那张图**：能画的东西和昨天一样多。
什么时候图里出现了文字，才是真正的质变。
