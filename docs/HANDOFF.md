## 下一个任务：M3.6 投机分配

### 已确认的实测分解（1080p×10k 曲线，`gpu_frame_path` 基准）

```
提取         2.03 ms   ← 纯 CPU，属 M7
分配         0.13 ms   ← 池化 26 处缓冲的全部收益上限
上传         0.97 ms
编码1a+提交  0.33 ms
编码1b+提交  0.09 ms
编码2        0.06 ms
提交2        0.08 ms
读回1        2.35 ms   ← 最大单项，其中约 1.4 ms 是纯 fence/map 延迟
读回2        0.20 ms
GPU 合计     2.83 ms
墙钟约 10.4 ms
```

### 两条原始依据已被实测否定（不要再做）

1. ❌「池化每帧重建的 ~26 个缓冲」→ 分配仅 **0.13 ms**。
   （wgpu 缓冲创建惰性，显存由驱动内部池化）
2. ❌「合并 3 次 submit」→ 三次编码+提交**合计仅 0.56 ms**。

### 正确的目标

**投机分配，消除读回1 的同步停顿（约 2.35 ms）。**

原理：稀疏结构规模只有 GPU 测量后才知道，所以原实现是
"提交 → 读回规模 → 分配 → 再提交"。改成把**上一帧实测的容量**作为本帧起点，
直接分配、不停顿；帧尾读一次实际用量更新容量。容量不足则**该帧作废、用实测值重做**。

### 建议的实现顺序（小步验证，每步跑测试）

1. 加 `SparseCapacity { cells, buckets, tile_entries, items, overflows }` 结构体
   + `GpuRenderer.sparse_capacity: Mutex<SparseCapacity>` 字段 → **编译 + 测试**
2. 只把 **readback1** 改成容量查表（容量有效则跳过读回）→ **编译 + 测试 + 测量**
3. 再把 **readback2** 改成容量查表 → **编译 + 测试 + 测量**
4. 帧尾加一次用量读回 + 溢出检测 + 容量更新 → **编译 + 测试**
5. 加重做路径（溢出时用实测值重跑一次；把现有函数改名为
   `run_pipeline_sparse_once`，外层加带重试的 `run_pipeline_sparse`）→ **编译 + 测试**

**不要把 2、3、4、5 合并成一次大改** —— 这正是上一次失败的走法。

### 正确性依据（关键，不可省）

- 容量不足时超出的写入会被丢弃（naga 对 storage buffer 有边界检查）
- 用量计数会如实超过容量 → 据此检测溢出并重做
- **绝不把残缺的画面交出去**

### 预期结果

墙钟约 10.4 → 约 8 ms。**再往下需要 M7**（提取 2.03 ms 是纯 CPU）。
