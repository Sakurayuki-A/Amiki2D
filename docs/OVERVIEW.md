## 一、项目定位

**在"通用 2D 渲染引擎"的前提下，拿回一件现有引擎普遍放弃的东西：
把「画布面积」从资源预算里去掉。**

主流引擎（Skia / Direct2D / Blend2D）的中间数据都与**画布面积**成正比：
4K 画布上什么都没画，照样占内存、照样烧带宽。Amiki2D 让占用只随**画面实际内容**增长：

| 场景 | 传统做法 | Amiki2D |
|---|---|---|
| 1080p，一万条曲线 | 20.93 GB（根本跑不了） | **34.5 MB** |
| 空画布 | 与画布等面积的开销 | **零分配** |

换成用户能感知的话：**让"画一万个元素"和"画十个元素"在内存与重绘成本上是一个量级。**
这对带文本和图表的界面、文档查看器、地图、数据可视化是决定性的。

### 必须承认的边界

这个设计**偏向"静态或缓变的、内容量大的"画面**（UI、图表、文档）。
对"整屏每帧全变"的场景（全屏游戏特效、视频播放），稀疏结构的开销反而**比传统渲染器更重**。

> 所以差异化不是"我们更快"，而是：
> **在其他引擎里空间和时间都随画布走的场合，我们让它们随内容走。**

### 三条立得住的机制

1. **解析式覆盖率**：不靠超采样，边缘是闭形式的面积积分 —— 任意缩放不糊，
   且没有 MSAA 那样的显存倍数（细节见 [RENDERING_STRATEGY.md](RENDERING_STRATEGY.md)）。
2. **稀疏分箱**：中间数据只与"实际画了什么"成正比，与画布尺寸无关。
3. **字形即路径**：字体轮廓直接进同一条管线，文本**不分叉**成第二条渲染路径 ——
   于是"文字的覆盖率精度"与"图形的覆盖率精度"是同一条数学。

### 2.1 渲染管线（M1–M6 / P0：从未登记为"限制"）

| 能力 | 说明 |
|---|---|
| **解析式覆盖率抗锯齿** | 圆 / 贝塞尔 / 自相交多边形；CPU 与 GPU 两条独立实现**逐像素一致**（容差 2/255，实测多为 0~1） |
| **路径填充** | **nonzero 与 even-odd 两种填充规则**（0.8.0）；16 种 W3C 混合模式 |
| **文字缓存**（0.10.1） | `Canvas::text_cached`：**调用方持有** `TextCache` 复用字形轮廓（与 `text()` 逐像素相同，实测 1.3×）；缓存键含字体身份，故不能由门面自动持有（见 5.4 的 D8） |
| **状态栈** | `Canvas::save` / `restore`（0.9.0）：**四项状态**（变换 / 混合模式 / 裁剪栈 / 填充规则）整体存取；深度 32，溢出/下溢**显式报错**；层内栈独立 —— 这是 UI 框架"局部状态"的基本假设 |
| **裁剪** | 矩形 / 路径裁剪，含嵌套裁剪栈 |
| **描边** | join（miter / round / bevel，含 miter limit）、cap（butt / round / square）、开放折线与闭合环、**虚线**（0.10.2） |
| **渐变** | 线性 / 径向 / 扫描；双端逐像素一致 |
| **位图** | 旋转 / 缩放 / 平铺（Repeat 采样器）+ **mipmap**（见 2.2 的 B4） |
| **字体样式属性**（0.10.7） | `Font::style()` 读字重/斜体（`OS/2` 表，缺表兜底）；`FontStyle::distance` 定义「按样式取最近」的取舍（斜体不匹配 1000 > 字重差上限 800）；**不做合成加粗/倾斜** |
| **GPU 路径**（0.10.8 复用 / **0.10.9 修掉 4K 静默错误**） | 渲染器进程级复用（每次调用 ≈100 ms → ≈1.7 ms）；**任意画布尺寸**都走 GPU —— "超 2048 回落 CPU"那条止血已随真因修复**删除**（真因是 1D 派发拆二维时宿主与内核行距不一致，与 `y` 无关）；4K/2000 矩形实测最大通道差 **0**、GPU 313 ms vs CPU 371 ms |
| **颜色矩阵滤镜**（0.10.4 类型层 / **0.10.5 接画布**） | `Canvas::set_color_filter`：**提交时**变换纯色 / 渐变停靠点 / 图像像素 ⇒ CPU/GPU 都不必知道滤镜存在（未动光栅器与 WGSL）。图像是逐像素（有代价）；**不在状态栈里**（有意，文档写明） |
| **九宫格贴图**（0.10.3） | `Canvas::image_nine`：四角**保持源尺寸不缩放**、边单向、中间双向（对齐 Skia `drawImageNine` / Android 9-patch）；实现是「取子图 + 普通矩形放置」⇒ CPU/GPU/AMK1 都不需要知道它存在 |
| **图像编解码**（0.10.0） | **自己读图**：PNG（含**索引色** / 1–16 位）解码 + PNG 编码 + JPEG 解码；在**可选 crate** `amiki-codec` 里 —— 核心四 crate 仍零第三方依赖 |
| **滤镜与离屏层** | 高斯模糊（多次 ping-pong）、投影、分组不透明度；含层场景的**帧路径合成**（GPU compute 直接合成，不读回） |
| **HDR** | `Rgba16Float` 贯穿渲染目标 / 层 / 模糊，>1.0 的值能穿过层边界存活；出口可选色调映射（见 2.2 的 B12 / B13） |
| **增量渲染（damage region）** | 只重画脏 tile；静态界面省 **96.5%** 的 tile 着色；层的脏区经 `inflated_bounds` 传播（模糊/投影不会漏边） |
| **工程护栏** | GPU 自洽检查（不依赖参照实现）、8 个场景的**输出快照哈希**、容量预检、分段计时 |

## 三、架构分层

```text
       ┌──────────────────────────────────────────────────────────────┐
 调用方 │  Rust: amiki（门面 Canvas）      C/C#/Node/浏览器: C ABI 或 WASM │
       └───────────────┬──────────────────────────────┬───────────────┘
                       │                              │
        ┌──────────────▼──────────────┐   ┌───────────▼───────────────┐
 文本线 │ amiki-text  →  amiki-layout │   │   （C ABI 只是薄封送层）   │
        │ 字体解析/shaping/字体栈      │   │  crates/amiki-capi        │
        │ 断行/禁则/对齐/段落          │   └───────────┬───────────────┘
        └──────────────┬──────────────┘               │
                       │ 字形轮廓 = 普通路径（PathEl） │
        ┌──────────────▼──────────────────────────────▼───────────────┐
 场景层 │ amiki-scene：Scene / Draw / Path / Paint / Layer / TextRun   │
        │              （零第三方依赖；引擎不认识"文本"这个概念）        │
        └──────────────┬──────────────────────────────┬───────────────┘
                       │                              │
        ┌──────────────▼────────────┐   ┌─────────────▼───────────────┐
 后端   │ amiki-raster（CPU 参考）   │   │ amiki-gpu（wgpu compute）    │
        │ 解析式覆盖率 + 稀疏分箱    │   │ 同一套数学的 WGSL 实现        │
        └───────────────────────────┘   └─────────────────────────────┘
                       ▲                              ▲
                       └──── amiki-math（共享数学）────┘
```

| crate | 职责 | 依赖 |
|---|---|---|
| `amiki-math` | `Vec2` / `Affine` / 贝塞尔 | **零依赖** |
| `amiki-scene` | 场景数据模型、编码流 AMK1、文本数据类型、字形缓存 | **零依赖** |
| `amiki-raster` | CPU 参考引擎：解析式覆盖率 + 稀疏分箱 | 零依赖 |
| `amiki-gpu` | wgpu 计算着色器引擎（13 个 WGSL） | `wgpu` / `bytemuck` |
| `amiki-text` | 字体解析（`ttf-parser`）、shaping（`rustybuzz`）、**字体回退** | 上两者 + 两个文本库 |
| `amiki-layout` | 断行 / 行高 / 对齐 / 段落 / 禁则 | `amiki-text` |
| `amiki` | 门面：`Canvas` 友好 API + 后端选择 | 全部（文本层可选） |
| `amiki-capi` | C ABI（手写 header 契约，本 crate 是唯一允许 `unsafe` 的地方） | 全部 |

**三条关键取舍**（都不是偏好，是业界共识或实测结论）：

1. **渲染器不认识"排版"**：`shape()` 产出的是"带位置的字形序列"，`Canvas::text()`
   吃的就是这个。Skia 的 `SkTextBlob` 同理；HarfBuzz 官方文档标题就叫
   [What HarfBuzz doesn't do](https://harfbuzz.github.io/what-harfbuzz-doesnt-do.html)。
   排版是**独立可选层** —— 只想画一行轴标签的调用方不该拖进整套排版引擎。
2. **字形轮廓 = 普通路径**：字体轮廓归一化成 `PathEl` 之后，压平 / 分箱 / 覆盖率
   全都是既有管线。文本因此**没有**专用渲染路径，也就没有"文字精度要单独调"的问题。
3. **mip 链与 LOD 只在 CPU 算**：着色器只读不看（不做 `log2`），消除浮点 ULP 漂移源，
   双端一致是结构性的而不是靠调容差（0.6.0 的取舍，见 `docs/DECISIONS.md`）。

| **B9** | 超长单词放不进 `max_width` | 排版层**报告** `overflow`，不硬切、不静默截断 |
| **B10** | 提取性能余量不大（0.59 vs 判据 0.8 ms，约 26%） | 机制明确（消除每帧分配），但复杂度上升会吃掉余量 |
| **B11** | 帧路径最大单项是"保护性同步读回"（4.3–4.6 ms） | 它买的是"绝不静默画出残缺帧"，**不作为性能目标** |
| **B14** | 并发创建 context，在**启用 Vulkan 校验层**时会崩进程 | wgpu 在 `debug_assertions` 下默认开校验层；**release 不受影响**。约束：**串行创建、并行使用**（写在 `amiki.h` 线程模型里） |
| **B16** | `\|W\| ≥ 2` 区域的边缘覆盖率**饱和**（**既有**精度限制，0.8.0 查明） | 自相交/同向重叠路径的边缘会略"胖"：五角星实测最大偏差 **0.1387**（≈35/255）。不报错、不崩；**even-odd 不受影响**（偏差 0.0027）。严格精度场景应避免自相交路径 |
| **B17** | **GL 后端要求 compute shader**；受限上下文（无窗口进程 / 老驱动 / 部分 ANGLE）里**根本起不来** | 0.9.1 起显式报 BACKEND_UNAVAILABLE（**修前是 PANIC** ✗）。改用 Vulkan / DX12 / CPU 引擎 |
| **B18** | **图像编解码**：**0.10.0 部分关闭** —— 已有 PNG（含索引色/16 位取高字节）解码+编码、JPEG 解码；**仍缺** GIF/WEBP/AVIF/HEIF/JPEGXL/… 与 JPEG 编码 | 见 [COMPARE_SKIA](COMPARE_SKIA.md) A-1；已做的在可选 crate `amiki-codec`（核心保持零依赖） |
| **B19** | 字体**只能从文件加载**（无系统字体管理） | 对照 Skia 的 10+ 个 fontmgr 后端；"列系统字体 / 按族名取"做不到 |
| **B20** | **效果生态单薄**：图像滤镜 2/28（仅模糊、投影）、**无颜色滤镜**、**无路径效果**（虚线等） | 先补虚线 + 颜色矩阵（**都不需要新架构**），见 [COMPARE_SKIA](COMPARE_SKIA.md) A-2 |

### 5.3 明确不做（已决定的边界，避免范围蔓延）

| registry | 项 | 理由 |
|---|---|---|
| **C1** | **双向文本**（阿拉伯 / 希伯来） | 面向特定语言；需要独立的 bidi 算法 + 字形重排序 |
| **C2** | **Knuth-Plass 全局最优断行** | 是排版**质量**提升，不是能力缺失；贪心断行已可用 |
| **C3** | **宽色域**（Display P3 / Rec.2020） | 色彩能力的另一半，与"通用 2D"正交（**HDR 已做，见 2.2**） |
| **C5** | CPU 引擎 **SIMD / 多线程** | 并行实测**无效**（从 2 线程起单调变差）；真实瓶颈是分配而非计算，且目标已达成 |

### 5.4 技术债（不是"能力缺失"，但要知道）

| registry | 项 |
|---|---|
| **D1** | `docs/` 与代码注释的历史漂移（**本次 OVERVIEW 重写就是在还这条债**；其余点仍需逐个核对） |
| **D2** | 两份文档示例标了 `ignore`，不在 `cargo test` 里执行 |
| **D3** | `clip_texs` 字段需要 `#[allow(dead_code)]`（有意为之，仅为持有生命周期） |
| **D4** | 基准用例只有一条"复用"口径，与"一次性调用"口径**不可比** |
| **D5** | even-odd 的跨度分解**没有缓存**：逐帧重画同一 even-odd 路径会逐帧重算（只影响 even-odd，正确性无碍）。缓存键与失效条件需要先想清楚，故未顺手做 |
| **D6** | 增量/持久路径（`PersistentRenderer`）的层**仍按全画布渲染** ⇒ 享受不到 0.9.2 的 2.7× 提速（正确性不受影响：两条路径产出逐字节相同） |
| **D7** | C ABI 把 `clip_depth` / `fill_rule` **各存了一份镜像**：0.9.0 的 `restore` 曾让它漂移（已修成「成功后重新读回」，但「同一状态存两份」的结构还在） |
| ~~D8~~ | ~~门面文本路径没有字形轮廓缓存~~ —— **0.10.6 关闭**：C ABI 侧把缓存挂到字体对象上（键含字体身份 ⇒ 不会串字体），Rust 侧用显式 `text_cached`；门面不自动缓存属**设计决定** |

## 六、路线图

### 6.1 已交付的版本线

| 版本 | 主题 | 关键交付 |
|---|---|---|
| `0.1.0` / `0.2.0` | 核心管线 | 解析式覆盖率、双压平器、稀疏分箱、AMK1 编码流 |
| `0.3.0` | 能力门槛 + 工程成熟度 | 描边、含层增量、帧路径层合成、**文本排版 + CJK 禁则 + 字距**、提取 −71%、启动 61 ms、文件拆分、API 稳定性 |
| `0.4.0` | **C ABI** | 手写 `amiki.h` 契约、三绑定示例字节一致 |
| `0.5.0` | **WASM + HDR** | 纯 CPU wasm（与原生字节一致）、`Rgba16Float` 全程、色调映射 |
| `0.6.0` | **mipmap** | 链只在 CPU 生成、LOD 只在 CPU 算、双端对拍 ≤1（关闭 B4） |
| `0.6.1` | **脏区派发修复** | 修掉 M4 起的静默错误（脏区不在原点时重算错 tile）；把并发创建 context 的崩溃查清为 **Vulkan 校验层**问题并写进 ABI |
| `0.7.0` | **字体回退** | 有序字体栈 + 缺字策略；老 API 零破坏；C ABI 80 个符号（关闭 B15） |
| `0.8.0` | **even-odd 填充规则** | 状态式 `set_fill_rule` + AMK1 v2 的 bit 12 + C ABI 82 个符号；实现靠**几何预处理**（覆盖率数学与 WGSL 一行未改）；顺带查明既有精度限制 B16（关闭 B5） |
| `0.9.2` | **层只渲染自己的区域** | 层子场景按 `inflated_bounds` 渲染（2.7×），输出逐字节不变 |
| `0.10.0` | **图像编解码** | 可选 crate `amiki-codec`：PNG（含索引色）解码/编码 + JPEG 解码；C ABI 87 符号；定调"核心零依赖 + 生态放可选 crate"（B18 部分关闭） |
| `0.10.9` | **异步渲染接进 C ABI + 4K 静默错误真修** | C ABI 三入口（`begin` / `poll` / `try_read`，符号 87 → 90）+ `AMIKI_ERROR_BUSY`：宿主可以把读回摊到下一帧（B11）；`PendingFrame::try_read` 在未映射缓冲上取像素的 panic 修掉；**4K 静默错误真因查明并修复** —— 1D 派发拆二维时宿主按"工作组"、内核按"元素"推进，两者差 64 倍（修后 4K/2000 矩形最大通道差 **0**、GPU 313 ms vs CPU 371 ms）；随之**删除** `GPU_MAX_SUPPORTED_SIDE` 那条止血 |
| `0.10.8` | **GPU 复用 + 止血** | 渲染器进程级复用（60×）；超 2048 明确回落 CPU（当时真因未明；**0.10.9 真修并删除该限制**） |
| `0.10.7` | **字体样式属性** | 读字重/斜体 + `distance` 取舍（样式匹配前置） |
| `0.10.6` | **C ABI 文本缓存** | 缓存挂在字体对象上（键含字体身份 ⇒ 不串字体）；**零新增 API**；D8 关闭 |
| `0.10.5` | **颜色滤镜接画布** | `Canvas::set_color_filter`：提交时作用于纯色/渐变/图像；未动光栅器与 WGSL；不在状态栈（B20 的颜色滤镜一项收窄） |
| `0.10.4` | **颜色矩阵（类型层）** | `ColorMatrix` 落地 + 6 条测试；接画布留到独立一轮（要动 CPU+GPU） |
| `0.10.3` | **九宫格** | `image_nine`：四角不缩放、边/中间拉伸；实现绕开 uv 子区间约定（取子图 + 矩形放置） |
| `0.10.2` | **虚线** | `dash_polyline` / `stroke_path_dashed` / `Canvas::stroke_path_dashed`；非法模式显式 `None`（B20 收窄） |
| `0.10.1` | **文本缓存入口** | `Canvas::text_cached`：缓存由调用方持有（缺字体身份则不能自动缓存，见 D8）；实测 1.3× |
| `0.9.0` | **状态栈** | `save` / `restore` 四项状态（变换 / 混合 / 裁剪栈 / 填充规则）；深度 32、溢出下溢显式报错、层内栈独立；C ABI 84 个符号；抓修 C ABI 的 `clip_depth` / `fill_rule` 镜像漂移；登记 D5 |

### 6.2 候选下一步（**尚未决策**，按"能消除哪一类风险"分组）

| 类别 | 候选 | 为什么值得做 |
|---|---|---|
| **字体样式匹配本体**（0.10.7 只做了前置） | 让 `FontStack` 按 `FontStyle::distance` 挑最近的粗/斜 | **形状已定（0.10.9 决策）**：把"请求样式"放在**栈**上 —— `FontStack { fonts, want }` + `set_style`，`resolve` / `resolve_in` 在**含该字形的字体里**取距离最近者（并列时保留先出现的 ⇒ 全 Regular 的栈行为与今天**完全一致**）；C ABI 加 `amiki_font_stack_set_style`（**+1 符号 = 91**）。shaper / 光栅器 / WGSL **都不用动**（缓存键本就含字体身份）<br>**为什么留到下一轮**：①要动公开 API 与 header 契约，该单独一轮；②想给出"真的选中了 Bold"的端到端证据，得往 `assets/fonts` 里加一份 Bold 字重（现在**只有两份 Regular**，那是当初为仓库体积刻意决定的）—— 这是资产决策，不该顺手做 |
| **还债** | `D1` 逐点核对 docs 与代码注释、`D4` 统一基准口径、`D2` 让 `ignore` 示例进测试 | 这些都是"文档/测试在骗人"的风险点，成本低 |
| **补齐已知短板** | `B6` CPU 侧含层增量、`B2` 字体格式（`.ttc`/`.woff`）、`B3` 编码流内嵌位图 | 都是**边界明确**的增量，不引入新架构 |
| **能力** | `B5` even-odd 填充、`C3` 宽色域、`A2` WASM 的 WebGPU（需要先解决同步/异步 ABI） | 需要新机制（绕数规则的第二种、色彩管理、异步初始化），不是"顺手加" |
| **性能** | `B10` 提取余量、`B11` 保护性读回 | 余量问题，目标已达成；除非场景复杂度上升 |
| **验证** | `A1` 跨厂商（需要第二块 GPU） | 技术上可验证，缺的是硬件；钩子已备好 |
