# Amiki2D 第一个发布版本计划（0.3.0）

> 本文回答一个问题：**第一个不带 `alpha` 后缀的版本，必须完成什么。**
>
> 不含时间估计（本项目只按依赖顺序推进，不给工期）。

---

## 一、发布目标

**一个"能画出完整界面、且在真实 UI 上兑现核心卖点"的版本。**

这句话有两个重点，各自对应一类门槛：

| 重点 | 含义 | 对应门槛 |
|---|---|---|
| **能画出完整界面** | 通用 2D 图元齐备 | 缺**描边** → 不能称通用 |
| **在真实 UI 上兑现核心卖点** | 增量渲染在**有滤镜的界面**上仍然有效 | 缺它 → 卖点在真实场景里失效 |

### 为什么是 0.3.0 而不是 1.0.0

- `0.3.0`：功能完备、可用于真实项目，但**不承诺 API 稳定**
- `1.0.0`：在 0.3.0 之上再加 **API 冻结**与**足够时长的 dogfooding**

先定 0.3.0，1.0.0 的判据见第五节。

## 二、P0 —— 能力门槛（缺了不能发布）

### P0-1 描边（stroke）

**为什么是门槛**：只有填充的 2D 渲染器画不出边框、图标轮廓、折线图、文字装饰。这是当前最大的能力空洞。

**范围**：
- join：`miter` / `round` / `bevel`，含 `miter_limit`
- cap：`butt` / `round` / `square`
- 闭合与开放路径
- 与填充一致的 paint 支持（纯色 / 渐变 / 位图）

**技术难点（必须先解决，否则会走弯路）**：

本项目用**解析式覆盖率**（每像素闭式线积分）做抗锯齿。描边的难点不是"怎么画粗线"，而是**重叠部分不能重复计入覆盖率**：

- 若把描边拆成"每段一个四边形 + join/cap 图形"，**相邻段在转角处必然重叠**，逐块积分再相加会**把 alpha 叠高**（半透明描边会出现深斑）
- 若先把路径偏移成单一闭合轮廓再填充，则要做**曲线偏移**（cubic 偏移不是 cubic，且 miter join 会截断）

**建议方向**：把描边表达为**有符号距离场意义上的"到路径距离 ≤ 半宽"**，而覆盖率积分直接对这个区域做 —— 即把"描边区域"看成若干**互斥分块**（按段的中点界划分转角归属），使每像素最多落入一个分块。这需要为"到线段的距离"推导闭式积分，而不是复用填充的积分。

**验收标准**：
- 与 CPU 参考实现对拍，最大通道差 ≤ 2/255
- 半透明宽描边在自交/急转角处**不出现深斑**（这是上面那个难点的直接检验）
- 任意缩放不糊（沿用解析覆盖率的既有性质）
- 与 Skia / Cairo 同场景目视对比无可见差异

### P0-2 含层场景的增量渲染 —— ✅ **已完成**

> 修掉了两个**静默错误**：`PersistentRenderer` 的增量分支从不合成层；
> `edit_damage` 完全忽略 `layers`（层内改动产生零脏区）。两者合起来是
> "有滤镜的界面从第二帧起悄悄丢掉滤镜"。
>
> 修法是三个缓冲分工：`base`（仅图元）/ `image`（最终）/ `layers`（已滤波缓冲缓存）；
> 脏 tile 上 `image ← base` 再按序叠层。全量与增量**共用**同一份层数学
> （`layer_buffer_from_content` + `blend_layer_rect`），不会漂移。
>
> 实测：带投影的静态界面 **3.5% tile 重画（省 96.5%）**，此前是 100%。
> 测试含 60 轮含层随机编辑序列与全量逐字节对拍。


**为什么是门槛**：M4 的 damage region 是核心卖点（静态界面省 96.5% tile 着色）。但**真实 UI 几乎都有阴影或模糊**，而当前 `render_damage` 一检测到层就**回落全量渲染** —— 等于卖点在真实场景里归零。

**当前状态**：

```
无层场景：静态界面省 96.5% tile 着色   ✅
有层场景：回落全量渲染，省 0%          ❌
```

**难点**：层合成需要把整层渲染到离屏纹理再读回，这与 damage 的"少读回、少重绘"直接冲突。

**建议方向**（三件事，按顺序）：
1. **层内也用 damage**：层有自己的脏区，只重绘层内的脏 tile
2. **层纹理跨帧复用**：层内容未变时**不重模糊**（模糊是层里最贵的一步）
3. **damage 传播**：层内容变化 → 层脏区 → 模糊膨胀（用已有的 `inflated_bounds`）→ 合成到主画布的脏区

**验收标准**：
- 一个**带阴影的静态界面**，连续帧的 tile 重画率 **< 10%**（当前 100%）
- 带模糊层的界面在只有局部变化时，重画率同样 < 10%
- 增量路径与全量路径**逐字节一致**（沿用 M4 已有的随机序列一致性证明方式）
- 层内容变化时，模糊半径内的**主画布** tile 必须全部标脏（否则会出现残影）

### P0-3 解掉逐帧路径对层的拒绝 —— ✅ **已完成**

> GPU 帧路径不再对含层场景报错，改为**在 GPU 上直接合成**（compute pass，不读回）。
> 三种滤镜 × 两条入口全部与参考一致：
>
> | 滤镜 | 与 `render_blocking` | 与 CPU | 帧持久路径 |
> |---|---|---|---|
> | `None`（分组） | 0 | 0 | 0 |
> | `Blur` | 1 | 1 | 1 |
> | `DropShadow` | 1 | 1 | 1 |
> | `DropShadow`（sigma=0） | 0 | 0 | 0 |
>
> **关键决定**：用 compute 而不是 render pass —— 调用方提供的输出纹理只有
> `STORAGE_BINDING | TEXTURE_BINDING | COPY_SRC`，没有 `RENDER_ATTACHMENT`
> 也没有 `COPY_DST`；compute 能写 storage texture，也只需要已有的 `COPY_SRC`
> 就能先把目标拷进 backdrop（W3C 混合需要背板）。
>
> 过程中修掉四个缺陷（含一个 **CPU/GPU 共用**的真 bug：`inflate_by_filter` 对
> DropShadow 把原点也平移了 `dx`，是平移而非并集 → 正偏移时裁掉左边/上边），
> 以及一个**参数传反**（`layer_tex` 与 `shadow_tex`）—— 后者只跟 `render_blocking`
> 对比会被漏掉，必须同时跟 CPU 对比才暴露。

## 三、P1 —— 性能门槛

### P1-1 CPU 提取的 SIMD 与多线程（M7 的性能项）—— 🔶 **部分完成**

**为什么是门槛**：帧路径 1080p×10k 是 10.00 ms，其中 GPU 只占 2.83 ms ——
墙钟是 GPU 的 3.5 倍，而差距主要在 **`提取` 2.03 ms（纯 CPU）** 与上传。

**已做**：
- 给 `cpu_extract` 基准补上 **1080p×10k** 用例（此前只有 720p×64 与 1080p×1000，
  而本项关心的正是 10k）
- 提取路径改为 `DrawPrims` + **容量预留**（10k 条 draw 不再反复扩容）

**实测**：

| 场景 | 改前 | 改后 |
|---|---|---|
| 帧路径 720p×64 | 486 µs | 487 µs |
| 帧路径 1080p×10k | 9.93 ms | **8.75 ms**（−12%，多次复测区间 8.6–9.3） |
| 提取（基准，一次性调用） | 2.03 ms | 0.887–0.982 ms |
| **提取（基准，复用缓冲）** | — | **0.586–0.617 ms** ✅ 判据 0.8 |

**被实测否定的一次尝试：每帧起线程。**
逐 draw 的提取互不依赖，我实现了一版"分块 + 按序归并"（顺序固定，结果与串行
**逐字节一致**），并设阈值避免小场景被拖累。**实测是净损失，而且单调变差**：

| 线程数 | 1080p×10k 提取 |
|---|---|
| **1（串行）** | **0.70–0.91 ms** |
| 2 | 1.02–1.68 ms |
| 4 | 1.18–1.53 ms |
| 8 | 1.22–1.69 ms |
| 12 | 1.27–1.62 ms |

**排查过程（每一步都实测）**：

1. 先怀疑线程创建开销 → 直接测：`thread::scope` + 12 个空 spawn = **304 µs**
   （不是我最初间接反推的 1.2 ms）
2. 再怀疑**分配器争用**（12 线程各自扩容 6 个 Vec）→ 改成"主线程预分配
   12 份缓冲、并行区只 push"→ **没有改善**（1.364 ms）
3. 最后用一个**纯计算对照**验证机器到底能不能并行：同机 12 线程做 sqrt 累加
   → **加速 4.43×** ✓

**结论**：机器能并行，是这个**负载**并行不了（剩余原因未定位）。
已按实测撤掉并行，并把上面两条诊断留成测试
（`measure_thread_scope_overhead`、`measure_actual_parallel_speedup`），
以免将来有人重走一遍。

真要做的话，正确方向是**常驻线程池**（只建一次、跨帧复用），而不是每帧
`thread::scope`；本项目刻意不引入 `rayon`，那需要一个基于 `std::sync::mpsc`
的小池子 —— 属于后续工作。

**未达标**，而且**其中一条判据在 P1-1 范围内不可能达成** —— 见下。

#### 附加发现：帧路径的构成（**含一次结论更正**）

`profile_frame_path_phases` 三次实测：

```
prepare 0.93–0.96 ms + render_into 5.13–5.74 ms + poll 0.01 ms = 7.51–7.90 ms
GPU 各 pass 时间戳合计 = 2.12–3.39 ms
```

> **更正**：本文件一度写过"帧路径 **86% 是 GPU 受限**，该判据不可能靠 CPU 达成"。
> **那是错的。** 它来自"`poll` 只花 0.01 ms"这个**推断**，而不是测 GPU 时间。
> 补上时间戳测量后，GPU 各 pass 合计只有 **2.1–3.4 ms**，占整帧 **27–43%**。

**分离实验结果：那 5.4–5.8 ms 的主因是「每帧一次 GPU 同步读回」。**

`sparse.rs` 的投机分配路径（容量已缓存 = 稳态）：

```rust
let (usage, overflow) = if speculative {
    let bytes = self.read_buffer(&stats_buf, 32)?;   // ← 每帧一次 GPU 同步
    prof.usage_readback_ms = ...;
    ...
}
```

代价约 **2.5 ms**（与"未归因"的 2.5–3.6 ms 吻合；profile 里首帧的
`读回1 2.41 + 读回2 0.19` 是同一件事的另一种形态）。

**而这个开销是有意为之的** —— 代码注释写得很清楚：

> 投机路径下分配值只是容量，**必须读回实际用量**才能判断是否溢出
> —— 溢出的那一帧画面残缺，由外层作废重做。

也就是一次 **"用 2.5 ms 同步换取'绝不静默画出残缺帧'"** 的取舍。
它直接对应发布判据第 3 条（没有静默错误路径）。

**所以「帧路径 < 6 ms」的现状是**：总 7.5–7.9 ms 中，
GPU pass 2.1–3.4、提取 ~0.95、上传+编码 ~1.2、
**溢出保护读回 ~2.5**。要压到 6 ms 以下，**必须动这个保护机制** ——
那是"正确性 vs 性能"的取舍，**不是纯优化**。可选的路径见 `DECISIONS.md` 第 ① 项。

#### 提取侧的真实瓶颈也不是遍历

`profile_extract_phases` 的分段：

| 分段 | 耗时 | 占比 |
|---|---|---|
| 只走路径（纯内存读） | 0.037 ms | 6% |
| **push 与装配** | **0.501 ms** | **82%** |
| 闭式段数计算 | 0.073 ms | 12% |

瓶颈是**每帧约 10 万次 `Vec::push`**，不是遍历（我原先以为是内存延迟）。
这解释了两件事：

- 为什么并行没用：push 是**写带宽 + 逐次边界检查**，不是可并行的长依赖链，
  且线程数曲线显示从 2 线程起就变差；
- 优化方向应该是**减少 push 次数**（例如合并 per-draw 数组），
  而不是"更快的遍历"。约 0.35 ms 的空间在这里。

#### 已做的优化（976→833 µs）

按"减少 push 次数"的方向做了两件事：

1. **合并 per-draw 数组**：原本每条 draw 要 push 5 次（colors / gradient_index /
   image_index / draw_clips / draw_flags），之后 `sparse.rs` 再把其中三个 zip 装配成
   `draw_meta`（又多 1 次）。改成在提取循环里**直接拼**，每 draw 从 4 次降到 **1 次**。
   稠密路径（仅基准与诊断）需要独立的 flags/clips 缓冲，在那里从 `draw_meta` 拆开。
2. **容量预留按真实图元数**：一条 draw 可贡献多个图元（**一个圆是 4 条三次曲线**），
   原先 `reserve(n_draws)` 只留 1 万位、实际要 4 万，仍然反复扩容；
   另有 per-draw 数组与 `counts` **完全没有预留**，已补上。

**剩余 4% 的明确方向**：`cubics` + `cubic_draws`（圆场景各 4 万次 = 8 万次 push）
与 `counts`（4 万次）。可行做法是把 `*_draws` 从"逐图元 push"改成
"末尾用 `Vec::resize` 按每 draw 计数一次性填充" —— 数据相同，但填充是批量写
而不是 4 万次带边界检查的 push。预估再省 40–60 µs。**未做。**

#### 判据改写（决策：保留保护机制，把判据拆成三项可测口径）

原判据是「帧路径总墙钟 < 6 ms」。实测后确认它把**三种性质不同**的东西
混在一个数字里：

| 口径 | 实测 | 性质 |
|---|---|---|
| **主机侧渲染**（提取 + 分配 + 上传 + 编码） | **2.55 ms** | P1-1 能优化的对象 → 判据 **< 3 ms** ✅ |
| **GPU pass**（时间戳） | **2.12 ms** | GPU 计算 → 判据 **< 5 ms** ✅ |
| **保护性同步读回** | 4.52 ms | **正确性开销** → 只设上限 < 6 ms，**不作为性能目标** |
| 总墙钟 | 7.5–8.1 ms | 记录在案，病态兜底 < 20 ms |

**为什么不去砍第三项**：那 2.5–4.5 ms 买的是"**绝不静默画出残缺帧**"
（投机分配的容量必须读回实际用量才能确认没溢出）。
发布判据第 3 条正是「没有已知的静默错误路径」——
为了一个性能数字去削弱它，方向是反的。

**新增的两个口径已写进代码**（`FrameProfile::host_render_ms` /
`safety_readback_ms`），并由 `profile_frame_path_phases` 断言锁定 ——
判据不再只是文档里的一句话。

#### 口径更正：提取**未达标**（我一度报成"临界达标"，那是错的）

发布计划记的原始值是 **2.03 ms**，那是 **`profile()` 的帧内单次采样**（`extract_ms`）。
而后来我引用的 `cpu_extract` 基准给的是 **criterion 均值**（0.83 ms），
**两者口径不同，不可直接比**。

补上同口径测量后（`profile().extract_ms`，3 次最小）：

| 口径 | 值 |
|---|---|
| **帧内（与 2.03 ms 同口径）** | **1.023 ms** ❌ 判据 0.8 |
| 隔离基准（criterion 均值） | 0.83 ms |
| 隔离基准（5 次最小） | 0.47 ms |

**所以：提取从 2.03 → 1.02 ms（−50%），但没有达到 0.8 ms 判据。**

这印证了我自己在更早一轮写下、后来又漂移掉的一句话：

> 隔离基准给的是**下界**，帧内数字才是真实成本。

**已做的两轮优化是真实有效的**（帧内 2.03 → 1.02 就是证据），
只是**还不够**。剩余缺口需要改数据布局（见下）。

#### 真正的根因：**每帧全新分配**（不是 push、不是 sqrt、不是 SIMD）

我先后提出并**实测否定**了三个方向，最后才找到真因：

| 假说 | 实测 | 结论 |
|---|---|---|
| 逐元素 push 比 memcpy 慢 | D2 0.289 ≈ D 0.298 ms | ❌ 预分配后都是带宽受限 |
| `sqrt` 是瓶颈（3 次/曲线） | 去掉全部 sqrt 只快 14% | ❌ 算术几乎免费 |
| 手工内联 / 无 sqrt 阈值版 | 0.313 / 0.277 vs 0.293 ms | ❌ 都在噪声内 |
| 4 条分块（向量化） | 0.195 vs 0.293 ms | ✅ 有效但只省 0.1 ms |
| **每帧全新分配** | 新建 **0.291** vs 复用 **0.053** ms | ✅✅ **差 5.3 倍** |

**真因**：`build_gpu_scene` 每帧要写约 **7 MB** 缓冲，全部**每帧新建**。
大于 128 KB 的分配走 `mmap`、释放走 `munmap`，于是**每帧重新缺页** ✗
那 0.236 ms/1.9 MB 的代价与写入内容无关 —— 这解释了为什么前面所有
"减少 push / 加快算术"的优化都没能动数字。

**修法**：新增
- `build_gpu_scene_into(scene, eps, &mut GpuScene)` —— 复用缓冲
- `GpuScene::reset_for_reuse()` —— 清空但保留容量
- `GpuRenderer::prepare_into(..., &mut Frame)` / `profile_into(...)` —— 逐帧 API
- `Frame` 内加 `clip_scratch`，clip 覆盖率纹理也复用

`build_gpu_scene()` / `prepare()` / `profile()` 保留为兼容包装（每次新建）。

**实测（判定基准 `cpu_extract`，三次）**：

| 用例 | 耗时 |
|---|---|
| `1080p_10k_curves`（一次性调用） | 887–982 µs |
| **`1080p_10k_curves_reused`**（引擎逐帧真实路径） | **586–617 µs** ✅ |

帧路径 `prepare` 也从 0.95 → **0.72 ms**。

> **注意**：`build_gpu_scene()` 的 887–982 µs **不是**引擎逐帧的成本 ——
> 引擎走的是 `prepare_into` → `build_gpu_scene_into`。判据看后者。

#### 曾考虑并撤销的方案：把段数计算移到 GPU

上一版本文档设计过一个"方案 A"：把 `uniform_segments` 的算术从主机移到
flatten pass。**已撤销，且判定为不需要** —— 根因是分配而非算术，
移走算术只能省 0.29 ms 里的极小部分，却要付跨侧改流水线的代价。

**撤销前弄清的一个要点**（记在这里，避免以后有人重新提出时再推一遍）：
这件事**不是"搬一段代码"那么简单**。flatten 的 dispatch 尺寸现在依赖
`total_segments`，而 `seg_end` / `seg_draws` 的缓冲大小也依赖它；计数移到 GPU 后，
这些值在 dispatch 之前就不知道了。解法是"**用保守上界驱动 dispatch、
让 flatten 按实际 `n` 提前退出**"，并让 scan 在 GPU 上写出真实的
`indirect` 参数 —— 也就是**把流水线从"主机驱动"改成"GPU 驱动"**。

> 该方案的完整设计曾单独成文（`docs/PLAN_EXTRACT_GPU_COUNTS.md`），

### P2-2 字距（kerning）—— ✅ **已完成**（并修掉一个相关真 bug）

**两个发现**：

**一、shaping 的字距本来就是生效的。** `shape` 累加的是 rustybuzz 的
`x_advance`，默认包含 GPOS 字距。实测 Inter 的 `AV`：V 的起点从
0.6899 em 收到 0.6216 em（**收紧 0.0684 em ≈ 7%**）。
所以"拿不到是遗漏"的猜测不成立 —— 缺的是**验证**。已补两条测试：
`kerning_is_applied`（AV 必须收紧）与 `non_kerned_pair_is_not_tightened`
（HH 不得收紧）。第二条是必要的对照，否则第一条可能只是"任何两字都被收紧了"。

**二、排版压根没用 shaping 的宽度（真 bug）。** `measure_chars` 逐字符累加
`font.advance_width(c)` —— 那是**不做 shaping** 的宽度，**既没有字距也没有连字**；
而同一文件里的 `measure_run`（断行后测行宽）用的却是 shaping 结果。
于是**排版宽度 ≠ 渲染宽度**：断行偏保守、`LayoutResult::size` 与画面也对不上。

**修法**：给 `amiki-text` 加 `shape_clustered`（返回字形及其 `cluster` 字节偏移），
排版据此把推进量映射回字符边界：

- 整段 shaping 一次（不是每个前缀各 shaping 一次，那是 O(n²)）
- 连字会让多个字符落在同一 cluster → 它们的前缀宽度相同（连字不可拆）
- shaping 失败时**回退并打印说明**，不静默给出不同结果

实测：单行 `AV` 的行宽 **131.15**（逐字符累加会得到 137.99），
与渲染宽度一致到 0.05 px 以内。

> **我自己踩的坑**：第一版测试把 `run.glyphs[i].x`（**em 单位**，字号在渲染时
> 才乘）与 `advance_width(...) * size`（**设备像素**）直接比较，断言写成
> "V 应从 74.32 收到 0.62" —— 看起来很荒谬，实际是单位错了，代码没问题。
> 已把单位写进注释。

### 多适配器验证的实质发现

**一、DX12 原本根本跑不起来 —— "一套 WGSL 通吃"当时是假的。**
`Backends::DX12` 下 `create_shader_module` 直接失败：

```
FXC D3DCompile error: amiki_fine(…): error X3511:
forced to unroll loop, but unrolling failed.
```

根因在**我们自己的 WGSL**：FXC 看到常量次数的循环会尝试展开以把下标静态化，
而下标依赖运行期值。三处这种写法：`int_clamped_linear` 的排序网络
（`ij[st]`、`ts[p.x]`）、`blend_color` 的 case 6/7/9（`o[i]`，**这处才是真正
报错的**）。全部显式展开后编译通过，且**数值逐位相同**（比较交换顺序未变）。

**二、GL 的着色器编译失败（一个字符）。** naga 生成的 GLSL 是
`textureSize(sampler2D, uint)`，驱动要 `int` —— 来源是我们 4 处
`textureLoad(clip_texN, gid, 0u)`。把 mip 层参数写成 `0`（i32）即可：
GL 从 **12 条失败**降到 **1 条**。

**三、GL 的位图读不出来 → 改为显式拒绝。**
现象归一：经采样器得 `(0,0,0,1)`（**GL 规范对"不完整纹理"的规定返回值**），
直接 `textureLoad` 得 `(0,0,0,0)` —— 该数组纹理在 GL 上是空的。
已排除：LOD 钳位、`textureSampleLevel` vs `textureSampleGrad`、辅助函数内联、
`write_texture` 行距 256 对齐、手工双线性（全部实测无效）。
判断是 wgpu/naga 的 GL 后端在 `texture_2d_array` 上的问题。
**按本项目一贯约定，不支持就显式报错，不静默画错。**

> **测量教训**：中途我从"最差像素从 (39,8) 移到 (8,8)、最大差 255→250"
> 推断 `textureLoad` 能取到数据。**这个推断是错的** —— 250 是测试场景垫底的
> 背景色 `rgb8(250,250,250)`，即"位图完全没有贡献"。
> **只看差值大小不足以判断，必须看实际值。**

### 启动开销：定位结论推翻了本计划原先的假设

分段实测：**`Instance` + 请求适配器占 86%**（默认配置 294.6 ms 冷），
而**全部 21 条管线只占 12.7 ms**。所以本计划原先写的
"用 PipelineCache / 惰性创建"**是错的** —— 那样最多省 13 ms。

| 配置 | 冷 | 热 |
|---|---|---|
| 默认（全部后端 → 本机选 Vulkan） | 337 ms | 202 ms |
| `AMIKI_BACKENDS=vulkan` | **154 ms** | 53 ms |
| `AMIKI_BACKENDS=dx12` | 2272 ms | 2093 ms |

DX12 慢是 FXC **运行期编译**着色器的固有代价。现代 DXC 会快得多，但
`wgpu` 的 `static-dxc` 特性依赖 `mach-dxcompiler-rs`，**在构建期用 curl 下载 DLL**
—— 与项目"保持依赖轻量"冲突（离线构建会失败），**不采用**。

**默认保持全部后端**：默认值要保证"哪台机器都能起来"，指定单一后端会削弱
"一套 WGSL 通吃"。（我一度把默认改成只用 Vulkan，快一倍，已按此理由改回。）
需要更快启动的应用可显式指定后端，或利用 `new()` 本就是 `async`、与窗口初始化重叠。

## 八点五、曾经的未复现问题 —— **已复现、已定位；测试侧已收口（0.6.1）**

**一次不可复现的测试瞬时失败**（`cargo test --workspace`）：

- 首次出现：P0-1 描边完成后的验证运行
- 当时的现象：`amiki-gpu --lib` 报 `error: test failed`，但日志里**没有留下 panic 信息**
  （PowerShell 把 `*>` 与 `2>&1` 混用，输出交错丢失）
- 之后连续 **8 次**运行全部通过，合计 119 条，无法复现

### 0.6.1 复现了它 —— 而且它从来不是"测试瞬时失败"，是**驱动级崩溃**

按当时的建议"把输出重定向到文件单独取 stderr"重跑，拿到了确定的症状：

```
test exited abnormally            ← 进程直接死掉，没有任何 panic 信息
exit code 0xC0000005              ← 访问违例（access violation）
```

**触发条件是并发度**（RTX 3050 / Vulkan / Windows，`cargo test -p amiki-gpu --lib`）：

| 运行方式 | 崩溃次数 |
|---|---|
| 默认线程（~16） | **4 / 6** |
| `--test-threads=4` | 0 / 4 |
| `--test-threads=2` | 0 / 4 |
| `--test-threads=1` | 0 / 12 |

可疑方向得到了证实：多个测试线程**同时** `GpuRenderer::new()`（枚举适配器 +
创建 `wgpu::Device`）会让整个进程崩掉。崩溃与具体测试无关（单线程整套
37 条全绿；崩在哪个测试取决于线程调度）。**但"并发创建"只是触发条件，
不是根因** —— 根因见下一节。

### 隔离实验：是"创建"崩，不是"使用"崩

一开始很难断言这**只是测试环境**的问题 —— 每个测试既创建又使用设备，分不开。
于是做了最小实验（16 线程，各阶段单独跑）：

| 场景 | 崩溃 |
|---|---|
| 16 线程**并发创建**（各自 new + 渲染） | **3 / 6** |
| 校验层关掉（`InstanceFlags::empty()`），同一负载 | **0 / 6** |
| 串行创建 16 个 → 16 线程**并发使用**（各用自己的） | **0 / 5** |
| 4 线程并发创建 / 并发使用 | 0 / 6 · 0 / 6 |

**结论**：崩的是**创建**，不是使用 —— 而且根因不在引擎、也不在显卡驱动。

### 根因：Vulkan **校验层**（0.6.1 更正）

上面那个"关掉校验层 0/6"是关键一列。顺着它查 Windows 事件日志，崩溃记录写得很清楚：

```text
Faulting application name: amiki_gpu-*.exe
Faulting module name: VkLayer_khronos_validation.dll      ← 校验层，不是驱动
Exception code: 0xc0000005
```

wgpu 在 `debug_assertions` 下默认把 `InstanceFlags::VALIDATION` 打开，Vulkan 后端
据此加载**校验层**；该校验层在并发创建 Instance/Device 时会崩。

**这解释了为什么它"不可复现"**：`docs/VERIFY.md` 的验证清单一直用
`cargo test --release`（校验层**关**），而那次失败发生在默认（debug）配置下 ——
**两次不是同一套条件**，所以怎么重跑都对不上。也说明：

- **release 构建不受影响**（发布给用户的应用没有这条约束）；
- 受影响的是 **debug 构建 / 显式打开 wgpu 校验的运行**（含 `cargo test` 默认配置）。

**ABI 侧的写法**（已写进 `crates/amiki-capi/include/amiki.h` 的「线程模型」、
`crates/amiki-capi/README.md`、`docs/API.md`，登记为 `docs/KNOWN_ISSUES.md` **B14**，
原 D5 作废）：ABI 原句"不同 context 之间可以并行"说的是**使用**，这一半**成立**；
缺的是"**创建要串行**" —— 不依赖构建类型，统一按串行创建写。

**测试侧的处理**：`amiki-gpu` 的 GPU 测试共用一个串行闸门（`tests.rs` 的
`GPU_TEST_LOCK` + `gpu()` 助手），同一时刻只存在一个 GPU 设备。默认线程下
**6 / 6 全绿**。代价是这台 crate 的测试串行（整套 ~7 s），换来的是确定性 ——
并且顺带消掉了"性能断言在并行环境里失真"这个反复出现的假失败来源。

> **注意"多少线程以下安全"不是承诺**：4 线程 0/6、16 线程 3/6，中间没细测，
> 阈值与驱动/机器相关。约束的写法是"创建要串行"，不是"线程数别超过 N"。
>
> **三种后续处置（尚未决策；因为发布构建不受影响，价值已变小）**：
> ① 引擎内部串行化创建（推荐：release 无竞争、代价可忽略，debug 下消除崩溃；
> 代价是给"引擎不做内部同步"加一个例外）；
> ② ABI 层用 `AtomicBool` 显式拒绝并发创建（符合"不静默出错"，但把偶发崩溃变成
> 必然失败）；③ 什么都不做（现状，只保留测试侧闸门）。见 B14。

> **两条教训**（值得留档）：
> 1. 当初判断"无法复现就没有可验证的修复"是对的，但**"没有 panic 信息"本身是一条
>    线索** —— 真正的 panic 会留下栈，而进程被三层之外的东西打死不会。下次遇到
>    "失败但无输出"，先区分这两类，再按并发度做梯度实验。
> 2. **"能复现"不等于"找到了根因"**：我先写出的是"驱动层并发创建会崩"，那只是
>    现象。是**"把嫌疑组件单独关掉"这一列对照**（校验层 0/6）才把根因钉到校验层上
>    —— 也多亏 Windows 事件日志直接写出了 faulting module。**归因要落到能指认的
>    模块上，而不是"底层"这种说法。**

## 九、主要风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **描边的解析覆盖率** | 重叠不重复计数是数学问题，不是工程问题；可能推翻"拆成图元"的做法 | 先用最小实验证明"单段粗线"的闭式积分，再处理 join；**不要一次做完** |
| **层的 damage 传播** | 模糊半径会使脏区膨胀，漏标一处就出残影（难发现） | 用**随机编辑序列**的一致性证明（M4 已有此方法），而不是手写几个用例 |
| **多线程与确定性** | 并行提取若改变浮点累加顺序，会破坏"与 CPU 逐字节一致" | 并行只做**分块**（每块内部仍串行），块间结果按固定顺序归并 |
| **CJK 断行的范围蔓延** | 禁则处理与断行规则可无限细化 | 只做**硬性禁则**（标点行首/行尾），不做完整的 JIS/GB 断行等级 |

## 十、与既有里程碑的关系

| 里程碑 | 本版是否包含 |
|---|---|
| M1–M3、M3.5 | 已完成 |
| M3.6 | **P1-1 补完**（剩余项依赖 M7 的 CPU 优化，正是本版的 P1-1） |
| M4 | **P0-2 补完**（当前在有层场景失效） |
| M5 | **P2-1 / P2-2 补完**（CJK 未验证、字距遗漏） |
| M6 | 已完成 |
| M7 | **只取性能项**；C ABI / WASM / HDR 推迟 |

**结论**：0.3.0 = 把已完成的 M4 / M5 / M6 在**真实场景**下补齐，加上缺失的基本图元（描边）与性能收尾。
