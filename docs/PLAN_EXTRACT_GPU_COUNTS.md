# 提取达标方案 A（段数计算移到 GPU）—— **已判定：不需要**

> ## ⚠️ **本方案已判定不需要（2026-XX）**
>
> 写这份设计时，我以为瓶颈是"段数计算的算术量"。
> 后续的根源调查证明**真因是每帧全新分配（mmap + 缺页）**，
> 改成跨帧复用缓冲后提取已达 **0.586–0.617 ms**（判据 0.8）✓
>
> 本文件**保留作记录**：它记录了当时排除掉的三个方向与推导过程，
> 但**结论已作废**。详见 `RELEASE_PLAN.md` 的「真正的根因」一节。
> 背景与实测数据见 `RELEASE_PLAN.md` 的「根源调查结果」。

## 一、要解决的问题

判据：`build_gpu_scene` 在 1080p×10k 圆（**40k 条三次曲线**）下 < 0.8 ms。
现状：**0.93–1.04 ms**（原始值 2.03 ms，已 −54%）。

实测构成：

| 分段 | 耗时 | 占比 |
|---|---|---|
| 只走路径 | 0.099 ms | 10% |
| **段数计算（`uniform_segments` × 40k）** | **0.293 ms** | **30%** |
| **push 与装配（写 1250 KB + 320 KB）** | **0.538 ms** | **58%** |

已排除的方向（**别再试**）：

- ❌ **无 `sqrt` 的阈值版**：与 sqrt 版完全一致（0/40000 不一致），
  但**只快 7%**（0.271 vs 0.293）—— 瓶颈是算术吞吐，不是开方延迟。
- ❌ **两遍法直出最终布局**：`data` 装配在 `sparse.rs`，
  **不在判据所测的 `build_gpu_scene` 里**；做了会让判据**变慢**。
- ❌ **逐元素 push 改 memcpy**：预分配后两者都是带宽受限，**无差别**
  （0.289 vs 0.298）。

⇒ 剩下的唯一出路是**把 30% 的算术从主机移走**。

## 二、为什么这在架构上是合理的

flatten pass **本来就逐条处理曲线**（它要按 `n` 把曲线切成折线）。
"这条曲线切几段"这个信息，**它的消费者就是 flatten 自己**。
主机算它、上传它、再由 flatten 读回来 —— 纯属绕路。

放到 GPU 上算，算术从"主机 1 个核串行"变成"GPU 几千个线程并行"，
而且数据已经在寄存器/缓存里。

## 三、设计

### 3.1 鸡生蛋问题的解法

现在的依赖链是：

```
主机算 counts → total_segments → flatten 的 dispatch 尺寸（wg = ceil(total/64)）
                             ↘ 缓冲大小
```

若 counts 改由 GPU 算，`total_segments` 在 dispatch 前就不知道了。解法：

**用一个保守上界驱动 dispatch，让 flatten 自己按实际 `n` 提前退出。**

```wgsl
// flatten.wgsl 伪码
let entry = gid.x / MAX_SEG;        // 上界 = MAX_SEG 段/条
let k     = gid.x % MAX_SEG;
let n     = uniform_segments(曲线);  // ← 在 GPU 上算（与主机同一公式）
if (k > n) { return; }               // 超出这条曲线的实际段数就退出
let t = f32(k) / f32(n);
cell_segs[entry_base + k] = eval(t);
```

- `MAX_SEG`：每条曲线的段数上界。**需实测确定**（对 ε=0.05，
  当前场景实测 `n` 的分布是多少？先在主机上统计一次再定，
  并留 2× 余量；超出上界时**显式报错**，不静默截断）。
- dispatch 尺寸 = `n_entries × MAX_SEG / 64`，**固定可知** ✓
- 输出缓冲按上界分配 ✓ 浪费可接受（稀疏路径本来就是投机分配 + 容量学习）

### 3.2 主机侧要改什么

| 位置 | 现在 | 改成 |
|---|---|---|
| `build_gpu_scene` | 逐条算 `uniform_segments` 填 `counts`，再 `total_segments = counts.sum()` | **不算**；只填 `n_entries` 与上界 |
| `counts` 缓冲 | 主机填好后上传 | **删掉**（GPU 自己算，或由一个前置小 pass 写进缓冲供 fine 用） |
| `total_segments` | 精确值 | **上界**；fine pass 读 GPU 写的实际值 |
| `FlattenParams` | 含 `n_quads/n_cubics/n_lines` | 加上 `max_seg` |

### 3.3 fine pass 需要 counts 吗

需要 —— 它要知道每条曲线的段数才能定位 CSR 区间。
两种做法：

- **(a) 让 flatten 顺带把 `n` 写进 `counts` 缓冲**（`if k == 0 { counts[entry] = n; }`）
  ✓ 简单，一次写入
- (b) fine 自己也算一遍 ✗ 重复算术

**选 (a)。**

### 3.4 稀疏路径的容量学习

`sparse.rs` 的投机分配依赖"测得实际用量"。
改后上界变大，**第一帧测得的上界用量会被缓存**，
后续帧按缓存分配 —— 逻辑不变 ✓ 只是分配得比实际大一些。

## 四、验收

1. `profile_extract_root_cause` 的 **B 从 0.93–1.04 降到 < 0.8 ms**
2. **150 测试全绿** —— 尤其 GPU/CPU 逐像素对拍
   （**上界截断必须显式报错**，不能静默少画）
3. `profile_frame_path_phases` 的三项口径不劣化
4. 主机侧 `counts` 相关代码**整段删除**，不留"备用路径"

## 五、风险与缓解

| 风险 | 缓解 |
|---|---|
| `MAX_SEG` 上界取小了 → 曲线被截断 | **显式报错**（本项目一贯取舍），并在文档写明上界是多少、怎么来的 |
| 上界取大了 → 缓冲浪费、flatten 空转 | 先在主机上统计一次 `n` 的真实分布（用一次性的诊断），按 2× 余量定；空转的线程会立即 `return` |
| WGSL 与主机的 `uniform_segments` 不一致 | 现在两者已经"逐式对应"（见 `amiki-math` 的注释），**移动而不是重写**这个公式 |
| 跨侧改动难测 | 每一步都让 150 测试跑一遍；**先加 GPU 侧路径、保留主机侧、用开关切换对比**，确认逐像素一致后再删主机侧 |

## 六、执行顺序（每步都可编译、可回退）

1. 加一次性诊断：统计当前场景 `n` 的分布 → 定 `MAX_SEG`
2. `flatten.wgsl` 加上"自己算 n + 按 k 提前退出 + `k==0` 时写 counts"
   （**先不动主机**，用一个环境变量开关切换新旧行为，对比输出）
3. 主机改成上界驱动 dispatch；确认对拍一致
4. **删掉**主机侧的 counts 计算与上传
5. 重测三项口径 + 全量测试；更新计划
