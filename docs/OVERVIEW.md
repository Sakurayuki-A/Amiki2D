## 一、一句话

**Amiki2D 现在能渲染图形和真字，但还不能排版。**

已经会画：矩形、圆、任意贝塞尔曲线、自相交多边形、16 种混合模式、裁剪合成、
**真实字体文本**（Inter，任意缩放不糊）、**渐变**（线性/径向/扫描）、**位图**
（含旋转/缩放/平铺）、**模糊与投影**（离屏层）。抗锯齿是**数学精确**的，
而且**特别省显存**；进一步地，**只重画改动过的地方**（静态界面省 96.5% 的重画工作）。

还不会：双向文本、图像缩放的 mipmap 过滤、全局最优断行。

**第一个发布版本（0.3.0）要完成什么，见 [RELEASE_PLAN.md](RELEASE_PLAN.md)。**

所以它现在**还不能直接用来做完整的 UI、文档、图表**——差的是排版。但**画面能力
已经足够画出像样的界面元素**了。用一句话概括：**能画出成品画面了，但写不出排版好的文字。**

## 二、它到底想成为什么

不是"又一个 Skia"。它想在**通用引擎**的前提下，拿回一件现有引擎普遍放弃的东西：

> **把「画布面积」从资源预算里去掉。**

主流引擎（Skia / Direct2D / Blend2D）的中间数据都与**画布面积**成正比：
4K 画布上什么也没有，照样占内存、照样烧带宽。

Amiki2D 让资源占用只随**画面实际内容**增长：

| 场景 | 传统做法 | Amiki2D |
|---|---|---|
| 1080p，一万条曲线 | 20.93 GB（根本跑不了） | **34.5 MB** |
| 空画布 | 与画布等面积的开销 | **零分配** |

换成用户能感知的话：**让「画一万个元素」和「画十个元素」在内存与重绘成本上是一个量级。**

这对带文本和图表的界面、文档查看器、地图、数据可视化是决定性的。

### 一个必须承认的边界

这个设计**偏向"静态或缓变的、内容量大的"画面**（UI、图表、文档）。
对"整屏每帧全变"的场景（全屏游戏特效、视频播放），稀疏结构的开销反而**比传统渲染器更重**。

所以真正的差异化不是"我们更快"，而是：

> **在其他引擎里空间和时间都随画布走的场合，我们让它们随内容走。**

## 三点五、最终路线图

```
1. C ABI          ✅ 已完成（0.4.0）
2. WASM           ← 下一项
3. mipmap（B4）   ← 有用户提再说
4. HDR            ← 最后
```

**为什么是这个顺序**：

- **C ABI 已落地**。它是"通用"这个词的兑现入口 —— 没有它，引擎再强也只是
  一个 Rust 项目；有了它，C# / Java / Node / Python 才进得来。
- **WASM 第二**。Web 是 2D 渲染器最大的分发渠道，而 C ABI 做完后 WASM 是自然延伸
  （Rust→WASM 直接编译）。不急在 C ABI 之前做，因为 **C ABI 的设计会直接影响
  WASM 的边界设计**。
  > 注意：现有的 `examples/node/` 用的是 **koffi FFI**，它证明的是"C ABI 能被
  > 非 C / 非 .NET 的运行时调进来"，**不是 WASM**。WASM 仍未开始。
- **mipmap 第三，但有用户提再说**。它需要动渲染管线（工程量不小），
  但决定能否进入地图、图像查看器、缩略图 UI 这些场景。
- **HDR 最后**。锦上添花，没有用户会因为它选你。

**已从路线图移除**：

| 项 | 处理 |
|---|---|
| **跨厂商验证（A1）** | **不做**。单人开源项目没有第二块 GPU，硬扛只会让路线图停摆。改成**已知限制**登记（`KNOWN_ISSUES.md` 的 A1），并留一个零成本钩子 `tools/verify_gpu.sh` —— 作者不跑，别人可能会跑 |
| CPU SIMD / 多线程 | 实测无效 + 目标已达成，保持"明确不做" |
| bidi / Knuth-Plass | 保持"明确不做" |

## 四、这次对话做了什么

分两类：**看不出画面的基础设施**（M3.5 / M3.6 / M4）与**看得出画面的新能力**（M5）。

### 看不出画面的部分

这些工作本来就是**不该改变画面**的那一类，每次都特意验证过"输出逐字节不变"。

| 做的事 | 打比方 |
|---|---|
| **M3.5** 工程硬化 | 装**验收用的检测设备和规矩** |
| **M3.6** 读回池化 | 拆掉一条**瓶颈管道** |
| **M4** damage region | 改成**只装修动过的那面墙** |

### M3.5：装了检测设备（已完成）

**问题**：以前如果渲染数学被改错，而且 GPU 和 CPU 两边**同时**改错，
现有测试会**通过**，bug 静默留下。历史上真的发生过一次（CPU 用自适应压平、
GPU 用均匀压平，两边不一致但很难发现）。

**现在**：加了两层独立的检查——
- **自洽检查**：不依赖任何"参照实现"，直接检查 GPU 内部数据结构是否自相矛盾
- **输出快照**：把 8 个场景的渲染结果用哈希钉死，任何非预期变化立刻失败

我实测过：故意改错一行，它立刻指出错在哪个场景、哪个单元。

### M3.6：拆了一条 85% 的瓶颈（部分完成）

**问题**：帧时间几乎全花在"从 GPU 取回数据"上（占 21.9 ms 里的 20 ms），
而且每次取回都新建一个缓冲、做一次冷映射。

**现在**：改成复用缓冲。实测 **720p 帧时间 6.59 ms → 1.03 ms（−85%）**。

### M4：增量渲染（已完成）

**目标**：从"每帧把整个画面重画一遍"变成"**只重画改动过的地方**"。

**已完成**：
- **脏区模型**：能表达"整幅全脏 / 部分脏 / 干净"三种状态，并量化到 tile 粒度
- **CPU 增量渲染**：只重算脏 tile，其余复用上一帧结果
- **正确性证明**：用 **200 轮随机改动的测试**验证"增量结果与全量渲染逐字节一致"
  （这是我特意用随机而非样例的原因——增量渲染最典型的 bug 是"特定序列下才错"，
  样例测试抓不住）

**已完成的部分**：渲染器跨帧记住上一帧。静态界面**省 96.5% 的 tile 着色**；
带离屏层的场景也有了脏区收益（P0-2，此前为 0）。

### 另外两件工程事项

- **发布了 `0.1.0-alpha` / `0.2.0-alpha` / `0.3.0-alpha`**，每次都补齐发布报告与变更记录
- **建立了 Git 版本控制**（这是我最后悔没早做的——中途我误把源文件改坏过一次，
  因为没有版本控制，只能靠你手动恢复存档）

## 六、接下来做什么，以及为什么是这个顺序

### 先分清两条线：渲染器线 vs 文本线

**这不是一条路线图，而是两条平行的线。** 混在一起会得出错误结论
（例如"渲染器应该实现换行排版"——那是错的）。

| 层 | 职责 | 归属 | 状态 |
|---|---|---|---|
| shaping | 字符 → 字形 id + 字距/连字 | `amiki-text` | ✅ 已有 |
| **布局** | **断行 / 行高 / 对齐 / 段落** | **独立可选层** `amiki-layout` | ✅ 已建（含 CJK 禁则） |
| 渲染 | 字形轮廓 → 覆盖率 → 像素 | `amiki-raster` / `amiki-gpu` | ✅ 已有 |

**为什么布局不属于渲染器**（这是业界共识，不是我的偏好）：

- Skia 的 `SkTextBlob` 只是"预先定位好的字形"的打包与渲染载体，**不含断行与段落**；
- HarfBuzz 官方文档标题即 [What HarfBuzz doesn't do](https://harfbuzz.github.io/what-harfbuzz-doesnt-do.html)
  —— **shaping 与断行是两件事**；
- 我们的 `amiki-text::shape()` 产出的 `TextRun` 已经是"带位置的字形序列"，
  门面 `Canvas::text()` 吃的就是这个。**渲染器一侧本来就没有排版概念，也不该有。**

而且布局**必须是可选的**：只想画一行字的调用方（图表轴标签、按钮文字）
不该被迫拖进一整套排版引擎。

### 渲染器线

| 里程碑 | 内容 | 状态 |
|---|---|---|
| M6 | 渐变 / 位图 / 滤镜（依赖层树做离屏合成） | ✅ **渐变 + 位图 + 滤镜全部完成**，CPU/GPU 双端逐像素一致 |
| M7 | CPU 引擎 SIMD + 多线程；C ABI / WASM / HDR | ⬜ |

### 文本线

| 里程碑 | 内容 | 状态 |
|---|---|---|
| M5 | 字形轮廓即路径 + shaping + 门面 API | ✅ **已完成** |
| M5.1 | 字体度量（ascent / descent / line_gap / x_height） | ✅ **已完成** |
| M5.2 | `amiki-layout`：断行 / 行高 / 对齐 / 段落 | ✅ **已完成**（贪心断行） |
| M5.3 | 双向文本、全局最优断行（Knuth-Plass） | ⬜ 明确不做（见发布计划第六节） |
| M5.4 | 字距（kerning） | ✅ **完成**（并修掉「排版未用 shaping」的真 bug） |

**布局层不需要新依赖**：`ttf-parser` 的 `Face` 已提供布局所需的一切——
`ascender` / `descender` / `line_gap` / `height` / `x_height` / `capital_height` /
`glyph_hor_advance` / `typographic_*` / `underline_metrics`
（且支持可变字体：`variation_axes` / `set_variation`）。

### 已完成的两步（它们让后面敢改）

**帧间持久化**：静态画面从"每帧全画"变成"几乎不画"——**第一个能感觉到速度的改动**，
但画面不变。实测静态界面省 **96.5%** 的 tile 着色。

**文字**：真实字体（Inter）文本已能渲染——`out/amiki_text_demo.png`，
窗口演示里有随时间缩放的真字。而且是**可测判据**：逐字形与 16× 超采样裁判对拍，
容差 0.03（与几何图形**同一容差**，说明文本没走"特殊照顾"的路径）。

### 暂时不做，以及为什么

| 不做 / 没做完 | 原因（**已按实测更新**） |
|---|---|
| CPU 提取的**常驻线程池** | 并行实测**无效**（从 2 线程起单调变差）。曾记的「固定开销 ~1.2 ms」**已被推翻**（实测 304 µs）—— 真实原因是**这个负载并行不了**。而且提取已达标，**不需要它** |
| **管线缓存** | 实测**没用**：启动开销 86% 在后端枚举，21 条管线只占 12.7 ms。已改「平台首选 + 全量回退」：**337 → 61 ms** |
| C ABI / WASM / HDR | 等内容能力更完整后再谈生态 |
| ~~CJK 字体入库~~ | ✅ **已做**：`NotoSansSC-Regular.ttf`（10.07 MB，OFL 1.1）随仓库分发，端到端验证不再依赖系统字体 |
| 换厂商 GPU 的验证 | **已决定收缩范围** —— 单人开发、只有一块显卡。记为「**已知未验证项**」而非「已通过」（见发布报告第六节） |

## 七、怎么自己看进度（不用读我的叙述）

```bash
cargo run --release -p amiki --example headless_png   # 出图（四张）
                                                      #   out/amiki_headless.png    图形能力
                                                      #   out/amiki_text_demo.png   真字 + 渐变
                                                      #   out/amiki_showcase.png    位图+渐变+文字+滤镜
                                                      #   out/amiki_paragraph.png   排版（断行/行高）
cargo run --release -p amiki --example window_demo     # 打开动画窗口（含真字）
cargo test  --workspace                                # 151 个测试
cargo bench -p amiki-gpu                               # 性能数据（含逐 pass 明细）

git log --oneline                                      # 开发时间线
```

`headless_png` 还会打印**可复现的量化证据**：
M4 增量渲染的脏区占比（全屏动画 vs 静态界面）、真字的像素数与字形数、
排版的行数与排版块尺寸。

**最诚实的进度说明就是那四张图**：`amiki_headless.png` 看图形能力，
`amiki_text_demo.png` 看文本，`amiki_showcase.png` 看位图/渐变/滤镜的综合效果。
